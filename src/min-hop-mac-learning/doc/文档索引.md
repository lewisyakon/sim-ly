## 当前一句话结论

当前版本的网络侧主路径可以概括为：

1. `sendflowclient` 是 Astra-Sim facade 和 3P 业务层入口。
2. `RoceTransportEngine` 只做逻辑层转换：`flow/lane -> qpn`、`REQUEST/DATA/ACT -> opcode/txClass`、3P FSM。
3. `RdmaPortEngine` 是每个物理端口上的 RoCE packet runtime，负责 `QP/SQ/RQ/CQ`、packetize、ACK、重传、reorder、pause-aware 准入和端口侧调度。
4. `PointToPointNetDevice + PppRoundRobinQueue` 是物理发送队列。当前 PPP 子队列按目的 MAC hash 分桶，再跨非空子队列 round-robin。
5. `MinHopBridgeNetDevice` 的 ingress 不是 per-qid 队列，而是每个 ingress port 一个 aggregate queue，每个包独立 token，经过 `switch_delay` 后 drain/retry。
6. GPU 端点采用 inner bridge 加可选 external bridge；外侧 terminal bridge 可以只学习，不承担 transit 转发。

## 最近验证结论

### RoCE 主路径

当前 RoCE 实现已经不再是早期“只有 3P 语义旁路”的状态。可以确认的主干能力包括：

- port-bound `QpRuntime`
- 最小 `SQ/RQ/CQ`
- transport ACK
- per-QP outstanding window
- timeout/retransmission
- bounded reorder buffer
- PFC / pause-aware admission
- bridge aggregate ingress queue

### 128 GPU AllToAll 与 PPP 队列

最近针对 [128_test.txt](/home/lja/sim-ly/sim-ly/simworkload/128_test.txt) 的 AllToAll 排查确认：

1. 上层 DATA 触发节奏没有因为 `drop_tail_queue_num` 改变而改变。
2. `drop_tail_queue_num=16` 时，当前目的 MAC hash 与 16 取模形成结构性碰撞，多个目的流落入同一个 PPP 子队列，RR 退化为子队列内 FIFO。
3. `drop_tail_queue_num=13` 打破了这类别名碰撞，尾部完成时间显著下降。
4. 这说明当前 PPP RR 的主要风险不是“不会轮询”，而是“分类键过窄，只按目的 MAC 分桶，遇到规律地址和特定队列数会退化”。

当前 13 队列日志来自 [128_random_test.log](/home/lja/sim-ly/sim-ly/simlog/128_random_test.log)：

- `network drained = 12.108us`
- `last FLOW_TX_DONE = 11.566us`
- `RX_DONE` 全局 spread 约 `0.952us`
- `TX_DONE` 全局 spread 约 `0.829us`

对照旧 16 队列临时结果：

- `network drained = 18.491us`
- `last FLOW_TX_DONE = 17.949us`
- `RX_DONE` 全局 spread 约 `14.364us`
- `TX_DONE` 全局 spread 约 `13.596us`

这部分后续如果继续改，应优先讨论“flow-aware qid classifier”或“per-flow DRR”，不要把 13 个队列当成长期机制本身。
