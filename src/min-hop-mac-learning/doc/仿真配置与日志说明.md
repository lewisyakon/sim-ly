## 1. 可视化配置面板

当前提供了一个轻量本地网页，用来编辑 `simconfig/config.json`：

```bash
python3 tools/config-ui/server.py --host 127.0.0.1 --port 8765
```

启动后在浏览器打开：

```text
http://127.0.0.1:8765/
```

这个网页只依赖 Python 标准库，不需要 npm、React、Electron 或额外安装包。

### 1.1 页面会做什么

配置面板会：

1. 读取 [simconfig/config.json](/home/lja/sim-ly/sim-ly/simconfig/config.json)。
2. 按“基础、拓扑、网络与 ECMP、PFC 与队列、RoCE、MAC 表、日志、专家 JSON”分组展示。
3. 把底层数字配置翻译成更容易理解的文本选项。
4. 根据当前拓扑隐藏不生效字段。
5. 保存时写回 `simconfig/config.json`。
6. 保存前生成备份：

```text
simconfig/config.json.bak
```

页面隐藏的兼容字段不会被自动删除。例如 FatTree 下 `topology.hostperleaf` 不生效，页面不会展示它，但如果原 JSON 里有这个字段，保存时仍会保留。这样普通用户不需要理解所有历史字段，专家也不会因为 UI 简化而丢失手工配置。

### 1.2 拓扑字段的条件显示

网页会按当前拓扑展示字段：

- `fattree`
  - 显示 `topology.k`、`subnet_model`、`subnet_k`。
  - 不显示 `hostperleaf`，因为 FatTree 不使用它。

- `clos`
  - 显示 `topology.k` 和 `hostperleaf`。
  - `hostperleaf` 表示每个 leaf 下挂多少 host/server 位置。

- `fullmesh`
  - 显示 `topology.k` 和 subnet 相关字段。

- `torus`
  - 显示 `topology.k` 和 subnet 相关字段。

- `external`
  - 显示 `topology.file`。
  - 不显示 `subnet_model` / `subnet_k`，因为 external 拓扑文件自己描述内外链路。

普通页面不再提供 `test` 和 `hpn` 下拉选项；历史 JSON 如果已经写了这些值，专家仍可在“专家 JSON”页直接处理。

### 1.3 ECMP 的文字选项

JSON 里 `network.ecmpmodel` 是数字；网页里显示为文字，保存时仍写回数字。

| 数字 | 页面显示 | 当前含义 |
|---:|---|---|
| `0` | 随机转发 | 每包随机选一个可用等价端口 |
| `1` | 按包哈希 | 源 MAC、目的 MAC、包 UID、本地 bridge 地址参与哈希 |
| `2` | 按流哈希 | 优先使用 flowTag；无 flowTag 时退回 UID |
| `3` | DATA 逐流喷洒 | DATA 按 flow 负载选择端口；非 DATA 退回随机 |

历史测试用 ECMP 值不会放进正式网页下拉框。若旧 JSON 中已经存在未公开值，网页会显示“当前 JSON 使用未公开值”，但普通用户应从上表正式选项中选择。

### 1.4 RoCE ACK timeout 的联动显示

网页里 `ACK timeout 模式` 会影响后续输入项：

- `auto`
  - 显示 `ack_timeout_factor`。
  - 代码会根据拓扑、链路速率、MTU、switch delay 和 `max_jump` 推导基础 RTT，再乘该系数。

- `fixed`
  - 显示 `ack_timeout_ns`。
  - 代码直接使用这个固定 timeout。

### 1.5 MAC 表目录自动生成

当前代码会按拓扑自动补 MAC 表目录后缀。网页也按同一规则生成普通拓扑的目录。

目录格式类似：

```text
mactable/topo-fattree_k-8_subnet-2_subnetk-8_gpusper-8_nvsper-1-python
```

其中：

- `topo-fattree`
  - 拓扑类型。
- `k-8`
  - 当前拓扑的 `k`。
- `subnet-2`
  - `subnet_model=2`，即 GPU fullmesh。
- `subnetk-8`
  - `subnet_k=8`。
- `gpusper-8`
  - 派生出的每 server GPU 数。
- `nvsper-1`
  - 派生出的每 server nvswitch 数。
- `python`
  - 用于加载已有 MAC 表。
- `flood`
  - 用于泛洪后导出 MAC 表。

当前规则：

- `mactable.load_enable=true`
  - 网页生成 `...-python`。
- 只开启 `mactable.dump_enable=true`
  - 网页生成 `...-flood`。

External 拓扑目录需要解析 `.topo` 文件才能知道 GPU、switch 和 link 数；网页当前不解析拓扑文件，因此 external 下保留手动路径。

### 1.6 静态内存估计

网页右侧会显示派生规模：

- 拓扑
- host/server 位置数
- GPU 数
- 交换机数

对 `FatTree + GPU FullMesh subnet`，网页会估计“泛洪结束后、业务 workload 开始前”的静态 RSS 量级。

当前估计模型分两段：

- `k >= 16`
  - 使用已有三组大规模数据校准模型。
- `k < 16`
  - 使用无截距量级模型，避免小规模被大规模模型里的负截距压成 `0GB`。

例如 `k=8, subnet_model=2, subnet_k=8` 会估计约 `0.6GB`，而不是 `0.0GB`。

这个值只用于配置前判断内存量级，不是运行期峰值保证。真实内存还会受日志、workload、事件队列、是否 dump/load MAC 表等影响。

## 4. 拓扑配置

配置路径：

```text
topology
```

### 4.1 `model`

当前普通页面主要暴露：

- `fattree`
- `clos`
- `fullmesh`
- `torus`
- `external`

代码历史上还支持：

- `test`
- `hpn`

但这两个不再放到普通 UI 下拉框里。

### 4.2 `k`

`k` 的含义依拓扑而定：

- FatTree
  - `k` 是 k-ary FatTree 参数。
  - 派生：

```text
numHosts = k^3 / 4
numCores = (k/2)^2
numAggregations = k^2 / 2
numEdges = k^2 / 2
switch_num = numCores + numAggregations + numEdges = 5k^2/4
```

- Clos
  - `k` 表示 leaf 数。
  - `numSpine = k / 2`
  - `numHosts = k * hostperleaf`

- FullMesh
  - `k` 表示 fullmesh switch/host 规模。

- Torus
  - `k` 表示 `k x k` 网格边长。

- External
  - 不靠 `k` 推导规模。
  - GPU、switch、link 数来自 `topology.file`。

### 4.3 `hostperleaf`

只对部分拓扑生效：

- Clos：每个 leaf 下挂多少 host/server 位置。
- HPN 历史分支：每个 ToR 下挂多少 host/server 位置。

FatTree 不使用该字段。网页在 FatTree 下隐藏它，但不会从 JSON 中删除。

### 4.4 `file`

External 拓扑文件路径。

只有 `topology.model="external"` 时生效。普通内置拓扑不会使用它。

External 拓扑文件格式见：

- [外部拓扑输入v1规格.md](/home/lja/sim-ly/sim-ly/src/min-hop-mac-learning/doc/外部拓扑输入v1规格.md)

### 4.5 `subnet_model`

服务器内 GPU 子网模型：

| 值 | 含义 | 派生 |
|---:|---|---|
| `0` | 无服务器内网 | `gpus_per_server=1` |
| `1` | NVSwitch | `gpus_per_server=subnet_k` |
| `2` | GPU FullMesh | `gpus_per_server=subnet_k` |
| `3` | GPU Torus | `gpus_per_server=subnet_k * subnet_k` |

External 拓扑不使用这个字段。

### 4.6 `subnet_k`

含义依 `subnet_model` 而定：

- `subnet_model=1`
  - 每 server GPU 数。
- `subnet_model=2`
  - 每 server GPU 数，且这些 GPU 全互连。
- `subnet_model=3`
  - server 内 GPU torus 的边长，GPU 数为 `subnet_k^2`。

### 4.7 `switch_delay_ns_override`

交换机处理时延覆盖值，单位 ns。

- 非 0：使用配置值。
- 0 或缺省：使用代码默认值。

当前常见：

- FatTree：`100ns`
- Clos：默认较大，历史代码中为 `5000ns`

- `normallink_delay`
  - 外部网络链路传播时延。
  - 例如 `"5ns"`。

- `nvlink_delay`
  - 服务器内链路传播时延。

## 7. PFC 与 PPP 队列配置

配置路径：

```text
pfc
```

这些字段虽然放在 `pfc` 下，但会直接影响端口队列、PPP 子队列和 RoCE 发送 admission。

- `drop_tail_queue_num`
  - `PppRoundRobinQueue` 内部子队列数量。
  - 当前 DATA 包按目的 MAC hash 后 `% NumQueues` 分桶。
  - 物理发送队列会跨非空子队列 round-robin。
  - `RdmaPortEngine` 的 qid/pause/admission 也按这个数量组织。

- `drop_tail_queue_size`
  - 每个 PPP 子队列容量。
  - bridge aggregate ingress queue 容量会按该值乘以 `drop_tail_queue_num` 派生。

- `high_watermark` / `low_watermark`
  - PFC pause/resume 水位。
  - 应满足：

```text
0 <= low_watermark < high_watermark <= 1
```

- `not_head_retry_ns`
  - 兼容旧配置保留。
  - 当前 bridge ingress 已经是 token-based drain/retry，不再使用旧的 not-head retry 队首模型。

### 7.1 AllToAll 中的队列数量经验

近期 128 GPU AllToAll 排查确认：

1. 上层 DATA 触发节奏没有因为 `drop_tail_queue_num` 改变而改变。
2. `drop_tail_queue_num=16` 时，当前目的 MAC hash 与 16 取模形成结构性碰撞，多个目的流落入同一个 PPP 子队列，RR 退化为子队列内 FIFO。
3. `drop_tail_queue_num=13` 打破了这类别名碰撞，尾部完成时间显著下降。

因此 `13` 是当前 workload 的有效 workaround，但不是长期原则。长期更合理的方向是 flow-aware qid classifier 或 per-flow DRR，而不是依赖某个特定队列数。

## 8. RoCE 配置

配置路径：

```text
roce
```

- `enable`
  - 是否启用 RoCE 旁路逻辑。
  - `true` 时发送/接收路径会附加并解析 `RoceSimHeader`，并启用 QP/FSM/ACK/重传等语义。
  - `false` 时走 legacy 逻辑。

- `data_use_write`
  - DATA 阶段是否默认使用 RDMA WRITE 语义。
  - 当前普通 UI 暴露这个字段，而不再暴露 `mode`。

- `mode`
  - 历史/高级字段。
  - 当前代码仍会读取它到 `g_roce_cfg.modeName`，并在 opcode 选择中参考 `read/send/write_only/rc_3phase` 这类字符串。
  - 但普通配置页面不再展示它；一般保持原值或通过专家 JSON 处理。
  - 如果未来确认完全不需要，应同时清理 C++ 中的 `modeName` 逻辑，而不是只从 JSON 删除。

- `sq_depth`
  - 默认 QP Send Queue 深度。

- `rq_depth`
  - 默认 QP Receive Queue 深度。

- `transport_ack_enable`
  - 是否启用 transport ACK、timeout 和 retransmission。
  - 关闭后，RoCE 仍保留 QP/调度语义，但不会进入当前 ACK/重传闭环。

- `transport_window_packets`
  - 每个 QP 同时允许存在的 outstanding packet 上限。
  - 达到上限后，该 QP 会暂停发送新的普通 packet，直到 ACK 释放窗口。

- `reorder_window_packets`
  - 每个 QP 接收侧允许缓存的 future packet 乱序窗口大小。
  - 当前约束：

```text
1 <= reorder_window_packets <= transport_window_packets
```

- `ack_timeout_mode`
  - ACK timeout 来源。
  - 推荐：
    - `"auto"`
    - `"fixed"`
  - 兼容：
    - `"manual"` 等价于 fixed 语义。

- `ack_timeout_factor`
  - 自动模式下，乘在 RTT 基线上的放大系数。
  - 近期为了避免 timeout 干扰队列分析，某些实验使用过很大的安全系数；不要把单次实验值当通用推荐。

- `ack_timeout_ns`
  - 固定 ACK timeout，单位 ns。
  - 在 fixed/manual 模式下直接生效。

- `max_retransmissions`
  - 单个 transport packet 最大允许重传次数。

- `ether_type`
  - RoCE 报文使用的二层 EtherType。
  - 可写 `"0x9999"` 或数字。

## 10. 主程序收尾时间日志

当前 `scratch/my_AstraSimNetwork.cc` 在 `Simulator::Run()` 返回后会额外输出两条主程序级时间：

```text
[main] network drained abs_time(ns)=... abs_time(us)=... abs_time(ms)=... since_workload_start(ns)=... since_workload_start(us)=... since_workload_start(ms)=...
[main] last FLOW_TX_DONE abs_time(ns)=... abs_time(us)=... abs_time(ms)=... since_workload_start(ns)=... since_workload_start(us)=... since_workload_start(ms)=...
```

这两条和 Astra-Sim 终端里的：

```text
all passes finished at time: ...
```

不是一个口径。

- `network drained`
  - 当前定义为 `sendflowclient` 视角下最后一次真实网络活动时间。
  - 它会在真实 `realsend()` 和 `HandleRead()` 上更新，因此更接近“网络侧最后一个包活动结束”的时刻。

- `last FLOW_TX_DONE`
  - 当前定义为最后一个 `[FLOW][TX_DONE]` 发生的时间。
  - 它更接近业务事务全部闭环的时刻。

- `since_workload_start`
  - 统一以 Astra-Sim workload `fire()` 的时间作为零点。
  - 当前默认对应 warmup 结束后的业务开始时刻。

建议按下面口径理解：

- Astra-Sim `all passes finished`
  - workload / stream 层口径。
- `[main] last FLOW_TX_DONE`
  - 3P 事务层口径。
- `[main] network drained`
  - 网络活动口径。

## 11. RoCE 配置与激活日志

示例：

```text
[ROCE][CFG] enable=true mode=rc_3phase dataUseWrite=true etherType=0x9999 logLevel=full transportAck=true transportWindowPackets=32 reorderWindowPackets=32 ackTimeoutMode=auto ackTimeoutBaseNs=2824 ackTimeoutFactor=2 ackTimeoutNs=5648 maxRetrans=8 reqOp=0 dataOp=2 actOp=0
[ROCE][ACTIVE] node=20 mode=rc_3phase dataUseWrite=true sqDepth=1024 rqDepth=1024 etherType=0x9999 logLevel=full transportAck=true transportWindowPackets=32 reorderWindowPackets=32 ackTimeoutMode=auto ackTimeoutBaseNs=2824 ackTimeoutFactor=2 ackTimeoutNs=5648 maxRetrans=8
```

字段含义：

- `enable`
  - 是否启用 RoCE。

- `mode`
  - 当前模式名。普通 UI 不再暴露，但日志仍可能显示历史配置值。

- `dataUseWrite`
  - DATA 阶段是否偏向 `WRITE`。

- `etherType`
  - 当前二层协议号。

- `logLevel`
  - 当前 RoCE 信息日志等级。

- `reqOp/dataOp/actOp`
  - 三个 3P 阶段映射到的 opcode。
  - 当前 `ACT` 是业务控制报文，不是 transport ACK。

- `transportAck`
  - 是否启用 transport ACK / timeout / retransmission。

- `transportWindowPackets`
  - 每个 QP 的 in-flight packet 上限。

- `reorderWindowPackets`
  - 接收侧允许缓存的 future packet 窗口。

- `ackTimeoutMode`
  - `auto` 或 fixed/manual。

- `ackTimeoutBaseNs`
  - 自动模式下，根据拓扑和链路参数算出的未乘系数 RTT 基线。

- `ackTimeoutFactor`
  - 自动模式下的放大系数。

- `ackTimeoutNs`
  - 当前实际使用的 timeout。

- `maxRetrans`
  - 单包最大重传次数。

## 12. Transport ACK / reorder / retransmission 日志

### `[ROCE][ACK][TX]`

含义：

- 接收侧发出了 transport ACK。
- 可用于观察累计确认点推进和接收侧状态。
- 通常在 `full/all` 等级下观察。

### `[ROCE][RX][REORDER_BUFFER]`

含义：

- 某个 future packet 进入接收侧 reorder buffer。

### `[ROCE][RX][REORDER_RELEASE]`

含义：

- reorder buffer 中连续可交付的数据被释放并上送。

### `[ROCE][RX][REORDER_OVERFLOW]`

含义：

- future packet 超出 `reorder_window_packets`。
- 当前策略是不缓存该包，继续只回累计 ACK，等待发送端 timeout/recovery 补洞。
- 这是 `WARN` 类日志，不受普通 RoCE info level 完全控制。

### `[ROCE][RTO]`

含义：

- outstanding 最老包触发超时，进入 recovery 处理。

### `[ROCE][RTX][SEND]`

含义：

- 某个重传包真正发出。

## 13. Bridge / PFC / 端点相关日志

### `[BRIDGE][RETRY][NO_PATH]`

含义：

- 普通 forwarding bridge 的某个 ingress 包在完成 `switch_delay` 后，当前没有可用出路。
- bridge 会保留该包并安排 ingress drain retry，而不是立刻丢弃。

当前实现说明：

- bridge ingress 不再使用按 qid 拆分的 `PppRoundRobinQueue` 作为缓冲。
- 每个 ingress port 只有一个 aggregate queue。
- 每个包入队后分配独立 token，并按自己的 token 在 `switch_delay` 后 drain/retry。
- `pfc.not_head_retry_ns` / `NotHeadRetryDelay` 目前仅为兼容旧配置保留。

### `[BRIDGE][TERMINAL][DROP]`

含义：

- 终端外侧 bridge 已经利用收到的 transit 包完成必要学习。
- 但该 bridge 不承担后续 transit 转发，因此在学习后停止转发。

当前说明：

- 代码里这条日志模板仍保留在 terminal-drop 分支。
- 默认 `NS_LOG_INFO` 输出已注释，避免大规模 flood 学习阶段日志爆炸。
- 看不到它不代表 terminal 分支不存在。

### `[PFC][THRESH][LOCAL][PAUSE/RESUME]`

含义：

- bridge 检测到本地注入队列达到高/低水位。
- 当前动作是通过 `FlowIo::PauseNodeQueue(...)` / `ResumeNodeQueue(...)` 控制本地软件发送队列。

### `[PFC][THRESH][NONLOCAL][PAUSE/RESUME]`

含义：

- bridge 检测到来自真实 ingress port 的队列达到高/低水位。
- 当前动作是向上游物理口回发 `PauseHeader`。

## 14. 事务流日志

这几类日志描述业务事务何时触发、何时收尾，不完全受 `roce.log_level` 控制。

### `[FLOW][REQ_DONE]`

示例：

```text
[FLOW][REQ_DONE] {tag,src,dst}= 5 0 1 workId=18 TIME=500000000000000000
```

含义：

- `REQUEST` 控制 work 的最后一个 slice 已经真正发出。
- 对应发送回调即将触发。

### `[FLOW][RX_DONE]`

示例：

```text
[FLOW][RX_DONE] {tag,src,dst}= 5 0 1 dataPackets=400/400 dataBytes=1638400 TIME=500000000000000000
```

含义：

- 接收侧已经收齐该 flow 的全部 DATA 分片。
- 接收侧会在这个时间点附近生成 `ACT`。
- 若上层已经登记接收回调，也会在这里附近回调 Astra-Sim。

### `[FLOW][TX_DONE]`

示例：

```text
[FLOW][TX_DONE] {tag,src,dst}= 5 0 1 actPackets=1/1 TIME=500000000000000000
```

含义：

- 发送侧已经收到该 flow 的最终 `ACT`。
- 该 flow 的发送完成回调会在这里触发。

### `TriggerSendTo_now declared now time = ...`

示例：

```text
TriggerSendTo_now declared now time = 500000000123456789 src=0 dst=1 tag=5 size=1638400
```

含义：

- Astra-Sim / `my_entry` 已经把一条点到点事务下放到 `sendflowclient`。
- 这是事务进入发送路径的最早观察点。

## 15. 异常与告警日志

### 15.1 `WARN` 类

这些日志通常不受普通 info log level 完全控制：

- `[ROCE][SQ][FULL]`
  - SQ 深度用尽，PostSend 拒绝该 work。
- `[ROCE][RQ][FULL] packet rejected before rx header`
  - RQ 已满，包在进入 QP 头处理前被拒收。
- `[ROCE][RQ][FULL] buffered packet rejected`
  - 需要进 reorder buffer 的包在占用 RQ 条目时失败。
- `[ROCE][RQ][FULL] packet rejected`
  - 正常上送路径占用 RQ 条目失败。
- `[ROCE][RX] QP rejected packet`
  - QP 引擎拒绝该包。
- `[ROCE][RX][REORDER_OVERFLOW]`
  - future packet 超出乱序窗口。
- `[ROCE][PORT][BUILD_FAIL]`
  - scheduler 选中的 slice 构包失败。
- `[ROCE][ACK][TX] failed to build ack`
  - ACK 包构建失败。
- `[ROCE][CQ][OVERFLOW]`
  - CQ 深度溢出，最老 completion 被挤掉。
- `[ROCE][SQ][COMPLETE_MISS]`
  - SQ 为空但收到完成通知。
- `[ROCE][SQ][COMPLETE_UNKNOWN]`
  - SQ 非空但找不到对应 `workId`。
- `[ROCE][SCHED] request callback missing`
  - REQUEST 收尾时未找到对应 send callback。
- `[ROCE][RX] missing/invalid RoCE header, fallback legacy parse`
  - 开启 RoCE 时收到无效头，回落 legacy 解析。

### 15.2 `FATAL` 类

这些通常直接终止仿真：

- `[ROCE][RX] ingress port engine missing`
- `[ROCE][SCHED] missing transport engine`
- `[ROCE][SQ] failed to prepare work`
- `[ROCE][SQ] failed to resolve tx port`
- `[ROCE][SQ] failed to post work`

## 16. 推荐排查顺序

一般排查时按下面顺序看：

1. 当前配置文件是否正确，优先用网页确认派生 GPU/交换机数量和 MAC 表目录。
2. `simlog/*.log` 里是否出现 `TriggerSendTo_now`。
3. 是否出现 `[ROCE][ACTIVE]`。
4. `[main] total send count` 是否大于 `0`。
5. 是否出现 `[FLOW][REQ_DONE] / [FLOW][RX_DONE] / [FLOW][TX_DONE]` 完整闭环。
6. 若怀疑队列分类问题，看 `drop_tail_queue_num`、`FLOW_RX_DONE/FLOW_TX_DONE` 全局 spread、是否无明显 drop/retrans/no_path。
7. 若怀疑乱序窗口或恢复机制问题，再看 `[ROCE][RX][REORDER_OVERFLOW]`、`[ROCE][RTO]`、`[ROCE][RTX][SEND]`。

## 17. 当前语义边界

1. 可视化配置面板是 `config.json` 的编辑器，不是完整仿真平台。
2. 页面不会自动运行仿真，也不会解析 external `.topo` 文件。
3. 页面隐藏字段不代表代码不支持该字段；隐藏通常表示普通用户不需要改。
4. `ACT` 是业务控制报文，不是 RC transport ACK。
5. `RoCE enable` 不等于完整 RNIC/verbs/RoCEv2/DCQCN 模型。当前是服务网络仿真的 `RC-like` 近似模型，已经具备 ACK、重传、reorder、窗口和 port admission 等关键网络行为，但仍不是完整现实 RNIC。
