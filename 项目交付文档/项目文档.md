## 1. 引言

随着大语言模型、多模态模型和推荐模型规模持续增长，AI 训练系统对算力集群的规模、互联带宽和通信稳定性提出了更高要求。当前主流训练系统通常通过多机多卡协同完成训练任务，单个模型训练过程会同时包含数据并行、张量并行、流水线并行、专家并行等多种并行策略，并由 AllReduce、AllToAll、ReduceScatter、AllGather 等集合通信原语支撑跨 GPU 的参数同步、激活交换和梯度规约。在这类系统中，网络已经不再只是提供基本连通性的基础设施，而是决定训练吞吐、尾延迟、资源利用率和系统扩展性的关键因素。

本项目面向大规模细粒度数据中心网络仿真需求，继承 SIMAI / Astra-Sim 的上层训练负载建模能力，并在 ns-3 网络侧补充数据中心拓扑、MAC 学习、ECMP、PFC、RoCE-like 传输和日志诊断能力。第三阶段重点围绕 RoCE 网络行为展开，目标是在不完整复刻 RNIC 内部实现的前提下，把会影响网络可见行为的关键机制下沉到仿真器中，从而支撑对万卡、十万卡 AI 集群网络行为的进一步研究。

### 1.1 研究背景与应用需求

近年来，AI 模型的参数规模和训练数据规模不断扩大。单机多卡已经难以满足大模型训练对显存容量、计算吞吐和训练周期的需求，实际工程中通常需要将训练任务扩展到数百、数千乃至更多 GPU 上。随着训练规模扩大，网络侧通信开销在端到端训练时间中的占比不断上升。即使单条链路带宽较高，集合通信中的突发注入、多路径负载不均、队列拥塞、PFC 回压、重传恢复和尾部流延迟仍可能成为训练性能瓶颈。

从训练并行策略看，数据并行依赖频繁的梯度规约，典型通信原语是 AllReduce 或 ReduceScatter；张量并行会在每层计算过程中引入细粒度通信；流水线并行需要跨阶段传递激活和梯度；专家并行则常通过 AllToAll 完成 token 或 expert 路由。这些通信模式在网络侧呈现出不同的空间分布、时间依赖和消息大小特征。例如 AllReduce 往往受环形或树形依赖链影响，而 AllToAll 更容易在短时间内形成多源多目的突发，对 ECMP、队列分类和交换机缓冲提出更高要求。

从网络技术看，AI 集群常采用高速以太网或 InfiniBand 等互联方案。基于以太网的 RDMA 方案 RoCE 在数据中心中应用广泛，其低 CPU 开销和低延迟特性适合训练通信，但 RoCE 的网络行为并不等同于普通无状态流量。一个可用于网络研究的 RoCE 仿真模型至少需要考虑 QP、PSN、发送窗口、ACK、超时重传、乱序处理、PFC pause、端口队列和路径选择等因素。否则，仿真结果容易退化为“应用层无限注入 + 链路带宽排队”的简单模型，难以解释大规模集群中的拥塞扩散、尾延迟和流间公平性问题。

在真实集群上直接开展大规模网络实验成本极高。首先，大规模 GPU 集群和高速交换网络资源昂贵，难以长期占用用于对比实验。其次，生产集群通常承载多租户任务，实验环境难以保持可控和可复现。再次，拓扑、链路速率、路由策略、队列机制和流控参数一旦涉及真实设备修改，就会产生较高运维风险。因此，构建一个能够同时覆盖训练 workload、集合通信、网络拓扑和传输协议行为的仿真平台，是进行大规模 AI 集群网络设计和优化的重要前置条件。

本项目正是在上述背景下展开。前期阶段已经完成了基本拓扑、workload 接入、集合通信负载生成和部分网络侧机制。第三阶段进一步聚焦 RoCE，尝试将影响网络可见行为的传输机制纳入 ns-3 细粒度仿真中，使平台能够更可靠地支撑后续的万卡/十万卡网络性能分析。

### 1.2 研究目标

本阶段研究目标不是重新实现一个完整训练框架，也不是逐周期模拟 GPU 内核，而是在已有 SIMAI / Astra-Sim 和 ns-3 基础上，提高网络侧行为的真实性和可解释性。具体目标如下。

第一，保持上层训练负载建模能力。项目继续利用 Astra-Sim 对训练 workload、集合通信原语和调度事件的抽象能力，将复杂训练过程转化为网络侧可处理的通信事务。这样可以复用前期阶段在混合并行、集合通信和 workload 文件格式方面的工作成果。

第二，完善数据中心网络拓扑和端点模型。项目需要支持 FatTree、Clos、FullMesh、Torus 等内置拓扑，并通过 external topology v1 支持用户输入边列表形式的自定义拓扑。同时，GPU 端点需要表达节点内部高带宽互联和外部后端网络端口，因此第三阶段继续完善 `innerBridge + externalBridge` 的端点模型。

第三，构建面向网络行为的 RoCE-like 传输模型。第三阶段重点是在端口侧实现最小 QP/SQ/RQ/CQ、传输层 ACK、每 QP 未确认窗口、超时重传、有界乱序缓存和感知 PFC pause 的端口准入，使仿真不再只依赖上层三阶段业务语义，而能表达传输层对注入速率、恢复过程和接收资源的约束。

第四，接通 PFC、bridge、物理队列和 RoCE 运行时。RoCE 在无损以太网络中通常与 PFC、队列和端口调度强相关。本阶段目标之一是让 bridge 队列水位、PauseHeader、PointToPointNetDevice 的 QueuePauseState、RdmaPortEngine 的 qid 准入和 PPP 子队列调度形成可观察闭环。

第五，建立可复现实验和日志诊断体系。平台需要通过统一 JSON 配置、本地配置 UI、主程序收尾日志、flow 事务日志、RoCE 传输日志、PFC/bridge 日志和 ECMP 日志，支撑从“现象”到“机制”的定位过程。尤其是在大规模 AllToAll 等突发通信中，必须能够区分问题来自上层依赖图、ECMP、PPP 队列分类、PFC、重传恢复还是 MAC 学习。

第六，明确模型边界。当前项目追求的是网络行为相似，而不是完整 RNIC 内部复刻。因此文档和实验需要明确：当前模型是 `PFC-aware RC-like RoCE` 近似模型，不是完整 RoCEv2 over UDP/IP，也不包含完整 ECN/CNP/DCQCN 闭环。

### 1.3 相关技术背景

#### 1.3.1 NS-3

NS-3 是面向网络研究的离散事件仿真平台，核心使用 C++ 实现。其基本建模单元包括 Node、NetDevice、Channel、Application、Queue 等。与只进行流级估算的模型相比，NS-3 更适合表达链路传播时延、序列化时延、队列排队、设备发送状态、事件调度和协议交互等细粒度网络行为。

本项目在 ns-3 中使用 PointToPointNetDevice 表达物理链路端口，使用自定义 MinHopBridgeNetDevice 表达交换机和 GPU bridge，使用 PppRoundRobinQueue 表达物理发送队列。由于项目目标是数据中心和 AI 集群网络，而非通用互联网协议栈，因此大量新增逻辑集中在 `src/min-hop-mac-learning/` 中。

#### 1.3.2 Astra-Sim

Astra-Sim 是面向分布式深度学习训练系统的仿真框架，能够将训练 workload、集合通信和系统调度转化为事件序列。它的优势在于能够从训练系统角度描述通信原语和并行策略，而不需要在网络侧手工编写每一条点到点流。

本项目将 Astra-Sim 作为上层 workload 驱动，网络侧通过 `scratch/my_entry.h` 与 `sendflowclient` 接收 `sim_send` / `sim_recv` 事件。这样可以把训练负载中的 AllReduce、AllToAll 等集合通信映射为网络侧可观察的点到点事务，并继续利用 ns-3 对底层网络行为进行细粒度模拟。

#### 1.3.3 RoCE/RDMA

RoCE 是在以太网上承载 RDMA 语义的一类技术。现实中的 RDMA 通信通常围绕 QP 展开，QP 包含 SQ、RQ、CQ 和状态机等资源。可靠连接类传输还涉及 PSN、有序接收、ACK、重传、超时、接收资源和完成记录等机制。RoCE 部署在以太网上时，还常与 PFC、ECN、CNP、DCQCN 等无损网络和拥塞控制机制耦合。

当前项目没有完整实现 RNIC verbs，也没有完整 RoCEv2 over UDP/IP 与 DCQCN。第三阶段采用的是面向网络行为的 `RC-like` 近似路线：保留会直接影响网络队列、回压、重传、乱序和尾延迟的关键行为，将它们放入 ns-3 端口运行时中；对不会直接影响当前网络侧实验目标的 RNIC 内部细节进行简化。

#### 1.3.4 数据中心网络拓扑

数据中心和 AI 集群常见拓扑包括 FatTree、Clos、FullMesh、Torus 以及厂商自定义拓扑。FatTree 和 Clos 通过多层交换结构提供多路径和较高的二分带宽；FullMesh 和 Torus 更适合表达特定规模或节点内互联；External topology 则允许用户通过拓扑文件描述更复杂或外部生成的连接关系。

本项目既保留内置拓扑构建逻辑，也引入 external topology v1。外部拓扑文件使用边列表表达 GPU、交换机、外网链路和内网链路，使用户能够通过脚本生成拓扑并接入当前仿真器。

#### 1.3.5 AI 集群网络关键问题

AI 训练通信具有突发性强、模式固定、同步依赖明显的特点。AllReduce 可能受环或树依赖限制；AllToAll 容易形成短时间内多源多目的突发；incast 和多目的 burst 会放大队列分类、PFC 和 ECMP 的影响。对于这类 workload，平均链路利用率不足以解释尾部完成时间，必须结合 flow 完成时间分布、PFC 活跃度、重传日志、队列分类和路径选择进行分析。

### 1.4 本阶段工作范围与主要贡献

第三阶段工作可以概括为：在已有 Astra-Sim workload 和 ns-3 网络构建基础上，重点完善 RoCE 网络行为、端口级传输运行时、PFC 与队列调度、外部拓扑输入和日志诊断体系。

本阶段主要贡献包括：

1. 将 RoCE-like 报文级运行时从 `sendflowclient` 业务层下沉到端口侧 `RdmaPortEngine`。
2. 实现端口绑定的 `QpRuntime`，显式维护最小 QP 状态、发送队列、接收资源和完成队列。
3. 实现传输层 ACK、每 QP 未确认窗口、超时重传、乱序缓存和完成记录。
4. 实现感知 PFC pause 的端口准入，使 RoCE 运行时能识别对应 qid 是否被暂停，以及该 qid 的在途报文数量。
5. 梳理 GPU 端点的 `innerBridge + externalBridge` 模型，并接入 external topology v1。
6. 建立覆盖配置、日志、RoCE 工作流、现实匹配性和仿真实验的文档体系。
7. 通过实机对比和大规模运行实验验证平台的精度与可扩展性，明确后续面向十万卡完整 workload 的优化方向。

## 2. 技术路线

本项目第三阶段采用分层解耦的技术路线：上层继续使用 Astra-Sim 表达训练 workload 和集合通信，下层使用 ns-3 表达网络拓扑、链路和事件调度，中间通过 `sendflowclient` 将训练通信事务转化为网络侧三阶段业务流，再通过 RoCE 逻辑层和端口运行时实现传输行为。整体路线可以概括为：

```text
训练 workload / 集合通信
  -> Astra-Sim 事件
  -> sendflowclient 三阶段事务
  -> RoceTransportEngine 逻辑 QP 和发送任务映射
  -> RdmaPortEngine 端口侧报文运行时
  -> bridge / ECMP / PFC / PPP 子队列
  -> ns-3 离散事件仿真
```

该路线的核心思想是：上层保持训练语义，底层补足网络行为，二者通过明确的 flow、tag、src、dst 和回调关系连接起来。这样既避免在网络侧重新实现训练框架，也避免把网络仿真简化为无传输约束的流量注入。

### 2.1 上层训练负载与集合通信建模路线

训练负载建模仍沿用 Astra-Sim 的 workload 文件。workload 文件描述模型层、通信原语、消息大小、并行组、GPU 数和执行阶段。例如当前 `simworkload/128_test.txt` 声明 `all_gpus: 128`，并包含 `ALLREDUCE` 和 `ALLTOALL_EP` 两类通信原语。这些原语经过 Astra-Sim 调度后，会转化为一组带有 `src`、`dst`、`tag`、`size` 的点到点通信事务。

网络侧并不直接理解训练层语义，而是通过 `scratch/my_entry.h` 接收 Astra-Sim 下发的 `sim_send` / `sim_recv`。随后 `sendflowclient` 以三阶段业务协议组织事务：

1. `REQUEST`：用于控制接收侧和业务回调。
2. `DATA`：承载实际数据传输。
3. `ACT`：用于发送侧最终完成闭环。

该路线保留了上层训练事件和网络侧 flow 的对应关系。日志中的 `TriggerSendTo_now` 表示 Astra-Sim 已经下发点到点事务；`REQ_DONE`、`RX_DONE`、`TX_DONE` 分别表示 REQUEST 发出、接收侧收齐 DATA、发送侧收到 ACT。通过这些日志，可以把训练负载中的集合通信阶段映射到网络侧完成时间和尾部行为。

采用这一建模方式的优点是：复杂集合通信仍由 Astra-Sim 负责展开，网络侧只需要处理统一的点到点事务和报文级运行时；同时，网络侧仍然能通过 `tag/src/dst` 识别 flow，为 ECMP、qid 分类器和日志统计提供稳定键。

### 2.2 网络侧细粒度仿真路线

网络侧采用 ns-3 作为离散事件仿真底座。拓扑构建、链路安装、bridge 绑定、应用安装和全局配置主要在 `scratch/my_common.h` 中完成。项目对 ns-3 原生 PointToPointNetDevice、queue 和 bridge 机制进行了扩展，使其能够表达 AI 集群后端网络中的 MAC 学习、PFC、ECMP 和端口调度行为。

网络侧拓扑路线分为两类：

1. 内置拓扑：通过 C++ 代码生成 FatTree、Clos、FullMesh、Torus 等结构。
2. 外部拓扑：通过 external topology v1 文件读取 GPU、交换机、外网链路和内网链路。

GPU 端点统一采用 `innerBridge + optional externalBridge` 模型。`innerBridge` 表达节点内部高带宽互联域，`externalBridge` 表达面向后端网络的外部端口集合。交换机节点使用 `MinHopBridgeNetDevice` 表达转发和学习行为，链路使用 PointToPointHelper 安装，并通过 `PppRoundRobinQueue` 提供物理发送队列。

MAC 学习和路径选择采用 warmup/flood 机制建立转发表。对于大规模重复实验，项目支持 MAC 表 load/dump 和 FatTree 计算式 MAC 表，以降低 warmup 成本。ECMP 则通过 `network.ecmpmodel` 控制，可选择随机、按包哈希、按流哈希、DATA 逐流喷洒以及专项实验模式。

该路线的关键是把网络侧行为留在 ns-3 事件系统中，而不是在上层用解析公式估算。链路速率、传播时延、交换处理延迟、队列容量、PFC 水位、端口忙闲状态和报文序列化时间都会通过事件调度影响最终日志时间。

### 2.3 RoCE 网络行为建模路线

RoCE 建模路线采用“网络行为优先”的原则。真实 RoCE/RDMA 系统包含复杂 RNIC 内部资源、verbs API、QP bringup、内存注册、CQ poll、SRQ、RNR、RoCEv2/UDP/IP、ECN/CNP/DCQCN 等机制。如果试图一次性完整复刻，会显著增加仿真复杂度，并影响大规模实验可运行性。因此第三阶段选择先实现对网络可见行为影响最大的部分。

当前模型重点实现以下机制：

1. QP、PSN 和接收侧期望序号：表达可靠连接中的顺序状态。
2. 发送队列、接收资源和完成队列最小模型：表达发送任务、接收资源和完成记录。
3. 每 QP 未确认窗口：约束单个 QP 的在途报文数。
4. 传输层 ACK：释放未确认报文并驱动窗口前进。
5. 超时、重传和恢复：表达报文缺口后的恢复成本。
6. 有界乱序缓存：表达乱序接收和窗口溢出。
7. 感知 pause 的端口准入：让 PFC pause 直接阻止对应 qid 发送。
8. 报文分片与可见 RoCE 头开销：让 MTU、链路占用和分片数量更接近真实传输。

为了保持职责清晰，RoCE 实现分为两层：

1. `RoceTransportEngine`：逻辑层，负责将业务流和阶段映射到 QPN、操作码、发送类别和 `workId`。
2. `RdmaPortEngine`：端口运行时，负责报文分片、ACK、重传、乱序处理、QP 状态、完成记录和端口准入。

这种分层避免 `sendflowclient` 继续承担报文级运行时，也避免 `RoceTransportEngine` 同时处理业务逻辑和物理端口状态。最终形成“业务层、逻辑层、端口层、物理队列层”的清晰边界。

当前路线明确保留若干简化：主路径不是完整 RoCEv2 over UDP/IP，没有 ECN/CNP/DCQCN 闭环，RQ 不是完整 posted receive/RNR 语义，CQ 也不是上层唯一完成驱动。因此当前模型的准确定位是 `PFC-aware RC-like RoCE` 近似模型。

### 2.4 配置、日志与可复现实验路线

为支撑大规模实验复现，项目采用统一 JSON 配置和分层日志体系。

配置路线包括：

1. 所有关键实验参数集中放在 `simconfig/config.json`。
2. 配置按 `network`、`topology`、`pfc`、`roce`、`mactable`、`logging` 等分组管理。
3. 本地配置 UI 负责把常用字段可视化，同时保留专家 JSON 入口。
4. 配置保存时生成备份，减少误改风险。
5. 通过 `--network_conf` 支持同一代码运行不同配置文件。

日志路线包括：

1. `[main]`：输出 `network drained`、`last FLOW_TX_DONE`、`total send count`、`total events` 等全局指标。
2. `[FLOW]`：输出 `REQ_DONE`、`RX_DONE`、`TX_DONE`，用于判断业务事务闭环。
3. `[ROCE]`：输出配置、激活、ACK、RTO、RTX、乱序处理、SQ/RQ/CQ 等传输信息。
4. `[PFC]`：输出 pause/resume 水位和传播行为。
5. `[BRIDGE]`：输出 NO_PATH、terminal drop、bridge drop summary 等路径和转发信息。
6. `[ECMP]`：输出候选端口、选路动作和 flow tuple，用于解释多路径分布。

实验分析遵循从上到下的诊断顺序：先确认上层是否下发 flow，再确认 RoCE 运行时是否激活，再看业务事务是否闭环，最后根据异常类型进入传输恢复、PFC、MAC 学习、ECMP 或队列分类分析。这样可以把现象归因到具体机制，而不是停留在“尾部流慢”或“整体时间偏大”的表面描述。

## 3. 实现方案

### 3.1 主路径与模块边界

第三阶段的实现主线可以从一条训练通信请求如何进入网络侧来理解。上层训练负载先由 Astra-Sim 展开为点到点通信事务，事务进入 sendflowclient 后，被组织成 REQUEST、DATA、ACT 三个业务阶段；RoceTransportEngine 再把业务阶段转成 RoCE 传输任务；RdmaPortEngine 负责在具体物理端口上切分报文、维护 QP 状态、发送 ACK、处理重传和乱序；最后报文进入 PointToPointNetDevice 和 PppRoundRobinQueue，由 ns-3 事件系统推动实际排队和发送。

这条路径的关键不是“多加了几个类”，而是把原来混在业务层里的传输行为拆开了。业务层只关心一条 flow 是否完成，RoCE 逻辑层关心这条业务动作应该落到哪个 QP 和哪种操作语义，端口运行时关心报文是否能发、是否被确认、是否需要重传，物理队列关心报文最终从哪个 qid 出队。

各层的职责可以概括如下。

(1) scratch/my_AstraSimNetwork.cc 是仿真入口，负责读取命令行参数、配置文件路径、日志路径，并在结束时输出主程序级统计。

(2) scratch/my_entry.h 是 Astra-Sim 与网络侧之间的接入层，负责把 sim_send 和 sim_recv 事件交给网络侧。

(3) sendflowclient 是业务事务层，负责 REQUEST、DATA、ACT 三阶段语义、业务回调、flow 级日志和最终事务闭环。

(4) RoceTransportEngine 是 RoCE 逻辑层，负责根据 flow、阶段和发送任务选择 QPN、操作码、发送类别和 workId。

(5) RdmaPortEngine 是端口侧 RoCE 运行时，绑定在实际 NetDevice 上，负责 QP 状态、发送队列、接收资源、完成记录、报文分片、ACK、重传、乱序处理和感知 PFC pause 的发送准入。

(6) MinHopBridgeNetDevice 负责 bridge 层行为，包括 MAC 学习、泛洪、ECMP、ingress queue、PFC 水位判断和出端口选择。

(7) PointToPointNetDevice 与 PppRoundRobinQueue 负责真实物理口发送、per-qid 子队列、轮询出队和 pause 状态传播。

这样的分层是第三阶段最重要的实现变化。RoCE 的报文级运行时下沉到物理端口以后，发送窗口、ACK、重传、乱序和 PFC pause 都发生在更接近网络设备的位置，仿真结果也更容易从日志上解释。

### 3.2 Astra-Sim 接入与三阶段业务流

上层 Astra-Sim 不直接操作交换机、队列或 RoCE 报文。它负责把训练 workload 中的集合通信展开为一组点到点通信事务，每条事务可以用 src、dst、tag、size 等字段描述。网络侧拿到这些事务后，不再关心它来自 AllReduce 还是 AllToAll，而是按统一的三阶段业务协议执行。

三阶段协议包括 REQUEST、DATA 和 ACT。

(1) REQUEST 是控制阶段，用来建立接收侧和业务回调关系。

(2) DATA 是真正承载业务数据的阶段，也是最容易形成队列拥塞和尾部延迟的阶段。

(3) ACT 是发送侧完成通知阶段，用来让发送端确认这条业务事务已经闭环。

sendflowclient 在这里承担两个任务。第一，它把 Astra-Sim 的点到点事务转成三阶段业务流；第二，它记录 flow 级日志，使后续实验能判断每条事务在哪个阶段完成。日志中的 TriggerSendTo_now 表示上层已经下发事务；REQ_DONE 表示 REQUEST 已经发出；RX_DONE 表示接收侧已经收齐 DATA；TX_DONE 表示发送侧已经收到 ACT，业务事务闭环。

ACT 和 RoCE 传输层 ACK 必须分开理解。ACT 是业务控制报文，说明三阶段事务结束；传输层 ACK 是 RoCE 端口运行时内部使用的确认报文，用来释放未确认报文、推进发送窗口和触发重传恢复。前者服务业务闭环，后者服务可靠传输。

### 3.3 RoCE 逻辑和端口实现

RoCE 相关实现分为 RoceTransportEngine 和 RdmaPortEngine 两层。RoceTransportEngine 回答“这次业务动作应该使用哪条 RoCE 状态”，RdmaPortEngine 回答“这条 RoCE 状态下的报文应该怎样切分、排队、确认、重传和完成”。

RoceTransportEngine 位于 sendflowclient 和端口运行时之间。sendflowclient 看到的是业务 flow，flow 可以表示为 {tag, src, dst}。其中 src 和 dst 是发送、接收 GPU 编号，tag 是上层集合通信展开后携带的通信标识。同一个 tag 在不同源、目的之间可能重复，所以不能只用 tag 作为传输状态的唯一键。

RoceTransportEngine 的主要职责如下。

(1) 根据 flow 和当前业务阶段分配 QPN。

(2) 将 REQUEST、DATA、ACT 映射为 RoCE 操作码。

(3) 为每一次业务发送任务分配 workId。

(4) 决定发送类别 txClass，使控制报文和数据报文能被端口侧区分。

(5) 维护三阶段业务状态，使 RoCE 传输细节不破坏 REQUEST、DATA、ACT 的业务顺序。

QP 是 Queue Pair 的缩写，可以理解为一条可靠传输状态的载体。QPN 是 QP Number，用来标识具体使用哪一个 QP。当前仿真器中的 QPN 不是通过真实网卡建链过程产生的，也不模拟完整 RNIC 连接管理，而是根据业务流和阶段生成稳定编号。这样做的目的是让不同业务流、不同阶段报文拥有相互隔离的发送窗口、接收顺序和确认状态。

RdmaPortEngine 是第三阶段最核心的新增类。它绑定在每个实际的 PointToPointNetDevice 上，代表该物理端口的 RoCE 运行时逻辑。一个节点可以有多个物理端口，因此也可以有多个端口运行时；每个端口运行时只管理自己绑定端口上的发送、接收、队列准入和传输状态。

在每个端口内部，RdmaPortEngine 以 QP 为单位维护运行时状态。这里的状态包括发送队列 SQ、接收资源 RQ、完成队列 CQ、未确认报文表、重传定时器和乱序缓存。

SQ 用来保存业务层提交但尚未全部发完的发送任务。这里的一个 SQ 条目不是一个 MTU 大小的网络包，而是一次业务发送任务。端口运行时会根据 MTU 把这个任务切成多个 RoCE 报文，并为每个报文填写 QPN、PSN、操作码和 workId。PSN 是 Packet Sequence Number，即报文序号，用于接收侧判断报文是否按序到达。

RQ 在当前实现中不是完整的 verbs post_recv 模型，而是一个简化的接收资源限制。接收普通 RoCE 报文前，端口运行时会检查该 QP 的接收资源是否已经达到上限。如果已经满了，报文不会继续推进协议状态，并会输出 RQ_FULL 类日志。这个简化不等同于真实 RNIC 的 RNR 机制，但已经能表达“接收端资源不足会影响传输”的网络行为。

CQ 用于记录发送完成和接收完成。当前 CQ 主要服务端口运行时统计和诊断，不是业务层唯一的完成驱动。业务层是否完成仍以 ACT 闭环为准。因此，看到 CQ 完成并不等价于 Astra-Sim 业务事务已经完全结束；判断业务完成仍应查看 TX_DONE。

一次 DATA 发送的端到端路径可以用下面的文字描述。

(1) sendflowclient 生成 DATA 业务动作。

(2) RoceTransportEngine 选择 QPN、操作码、workId 和 txClass。

(3) RdmaPortEngine 将发送任务写入对应 QP 的 SQ。

(4) RdmaPortEngine 按 MTU 把发送任务切成多个 RoCE 报文。

(5) 端口侧检查发送窗口、PFC pause 和 qid 准入。

(6) PointToPointNetDevice 发出报文。

(7) 接收端 RdmaPortEngine 检查 RQ、PSN 和乱序缓存。

(8) 接收端发出传输层 ACK，并在可交付时上送 DATA。

(9) 发送端收到 ACK，释放未确认报文和发送窗口。

这样拆分以后，业务层、逻辑层、端口层和物理队列层的边界比较清楚。后续如果增强重传、增加拥塞控制或改进队列分类，都可以在对应层内扩展，不需要继续把所有逻辑堆在 sendflowclient 中。

### 3.4 可靠传输机制

可靠传输机制主要由 RdmaPortEngine 承担。它不是简单把一个大消息直接送到链路上，而是先把业务发送任务切成 RoCE 报文，再围绕 QP 维护报文序号、发送窗口、ACK、超时重传和乱序接收状态。

报文分片首先受 MTU 影响。RoceSimHeader 会根据操作码带来不同的可见头开销。SEND 类报文的头开销较小，WRITE 或 READ_REQ 类报文的头开销更大，ACK 或 READ_RESP 类报文也有自己的头开销。这些开销会进入 MTU 预算，因此会影响分片数量、链路占用和排队时间。

传输层 ACK 用来释放发送侧的未确认报文。接收侧普通报文被 QP 接收状态接受后，会生成 ACK。发送侧收到 ACK 后，会读取 ACK 携带的确认序号 ackPsn，清除该 QP 上序号不大于 ackPsn 的未确认报文。如果未确认表已经清空，端口运行时会取消重传定时器；如果仍然有未确认报文，则重新设置定时器。

发送窗口用于限制单个 QP 同时在网络中的报文数量。当前由 transport_window_packets 控制。当未确认报文数达到窗口上限时，该 QP 会暂时停止发送新的普通报文，直到 ACK 返回并释放窗口。这样可以避免上层 workload 一次性无限注入，把传输层约束显式放进仿真。

超时重传围绕“最老未确认报文”工作。当前每个 QP 使用一个重传定时器。定时器触发后，端口运行时会找到最老的未确认报文；如果它还没有超过最大重传次数，就把它放入待重传队列，并进入恢复状态。恢复状态下，该 QP 会优先补齐缺口，而不是继续发送新的普通报文。

PFC 场景下，重传不能简单理解为“定时器一响就立刻重发成功”。如果对应 qid 被 pause，重传报文仍然会受到端口准入限制。当前实现只在报文真正重发成功时增加 retry 计数，因此不会在 pause 期间快速耗尽重试次数。

乱序处理围绕 expectedRxPsn 工作。接收侧看到小于 expectedRxPsn 的报文，会认为是旧包或重复包；等于 expectedRxPsn 的报文可以直接推进接收状态；大于 expectedRxPsn 但仍在 reorder_window_packets 范围内的报文会进入乱序缓存；超过窗口的报文会触发乱序窗口溢出。缺口补齐后，连续可交付的缓存报文会被释放给 sendflowclient 的三阶段处理逻辑。

这一组机制使当前模型不再是“业务层直接把流量打进链路”的简单模型，而是具备窗口、确认、恢复和接收顺序约束的 RoCE-like 传输模型。

### 3.5 PFC、bridge 与物理队列

PFC、bridge 和物理队列共同决定报文能不能进入下一跳。RoCE 逻辑本身只说明某个报文应该发送，但真实网络行为还取决于出端口是否可用、队列是否达到水位、上游是否被 pause、同一个物理口下有多少 qid 正在竞争。

MinHopBridgeNetDevice 的 ingress 当前采用每个 ingress port 一个 aggregate queue。也就是说，包进入 bridge 后先进入该 ingress port 对应的聚合队列，每个包分配独立 token，经过 switch delay 后再尝试 drain 或 retry。这个模型表达的是 bridge 处理延迟和有限缓冲，不在 ingress 侧重复实现 per-qid 调度。

per-qid 调度主要由物理发送队列承担。PppRoundRobinQueue 是物理口发送队列，内部包含多个子队列。当前 DATA 包默认按目的 MAC hash 后对 NumQueues 取模，决定进入哪个 qid。出队时，队列在非空且未暂停的 qid 之间轮询。

这个机制能表达多队列发送，但也带来一个重要风险。如果多个 flow 因目的 MAC 地址规律和队列数取模碰撞落入同一个 qid，round-robin 只能看到一个活跃子队列，实际就会退化为该 qid 内部 FIFO。因此，大规模多目的通信场景中仍需要关注 qid 分类是否足够分散。

PFC 当前分为两层。

(1) bridge / 本地注入层根据 ingress queue 和 egress queue 水位触发 pause 或 resume。对于本地注入，bridge 通过 FlowIo 暂停或恢复本地软件发送队列。

(2) 物理口 / RoCE 运行时层由 PointToPointNetDevice 更新 QueuePauseState，RdmaPortEngine 感知 qid pause 或 resume，并阻止或恢复对应 qid 的发送准入。

这种分层的目的，是让 pause 不只是日志事件，而是能真正影响端口发送。报文进入 RdmaPortEngine 后，即使 QP 窗口允许发送，如果对应 qid 被 pause，也不能继续进入物理队列。这样 PFC 回压、RoCE 发送窗口和物理队列状态之间可以形成闭环。

### 3.6 拓扑与端点模型

拓扑模型决定 GPU、交换机和链路如何被创建，也决定 MAC 学习、ECMP 和 RoCE 报文最终在哪些端口之间移动。当前项目同时保留内置拓扑和 external topology 两条路线。

内置拓扑主要包括 FatTree、Clos、FullMesh、Torus 等。正式实验中使用较多的是 FatTree、Clos 和 external topology。FatTree 中，topology.k 表示 k-ary FatTree 参数。Clos 中，topology.k 表示 leaf 数，hostperleaf 表示每个 leaf 下挂的 host 或 server 位置数。

服务器内 GPU 子网由 subnet_model 和 subnet_k 表达。

| subnet_model | 含义 |
|---:|---|
| 0 | 无服务器内 GPU 子网 |
| 1 | NVSwitch |
| 2 | GPU FullMesh |
| 3 | GPU Torus |

GPU 端点采用 innerBridge 加 optional externalBridge 的模型。innerBridge 表达 GPU 内部高带宽互联域，externalBridge 表达 GPU 面向后端网络的外部出入口。endpoint MAC 统一取 innerBridge 的 MAC。

外侧 bridge 不是普通 transit bridge，而是端点外部出入口和学习载体。它可以学习必要 MAC 信息，但不承担普通 transit 转发。这个设计为后续多 rail、多口端点和更复杂的内外网组合保留了空间。

External topology v1 使用文本边列表描述拓扑。文件先声明 GPU 数和交换机数，再声明外网链路数量和外网边，最后声明内网链路数量和内网边。编号规则是：GPU 编号从 0 到 N-1，交换机编号从 N 到 N+M-1。

External 拓扑中，外网链路允许 GPU-Switch、Switch-GPU、Switch-Switch，不允许 GPU-GPU；内网链路只允许 GPU-GPU。v1 格式目前不表达每条链路单独速率、延迟、plane、rail 或 pod 语义，也不会自动计算图直径。因此 external 实验需要用户显式检查 network.max_jump、warmup 时间和 ACK timeout 是否覆盖实际路径。

### 3.7 MAC 表与路径选择

MAC 表决定一个 bridge 在收到目的 MAC 后应该从哪个端口转发。项目当前支持三种 MAC 表使用方式：运行时学习、从已有目录加载、以及对特定 FatTree 场景使用计算式 MAC 表。

运行时学习依赖 warmup 和 flood。第一次跑新拓扑时，可以让 bridge 通过泛洪学习路径，并在学习完成后导出 MAC 表。后续重复实验时，可以直接加载已有 MAC 表，减少 warmup 成本。

mactable.load_enable 表示从已有目录加载 MAC 表。mactable.dump_enable 表示在学习后导出 MAC 表。mactable.computed_enable 表示使用计算式 MAC 表。当前 computed 模式只针对 FatTree 且 subnet_model 为 2 的场景验证过，不能和 load 或 dump 同时启用。

ECMP 决定多条可用路径之间如何选择。network.ecmpmodel 当前常见取值如下。

| 值 | 含义 |
|---:|---|
| 0 | 随机转发 |
| 1 | 按包哈希 |
| 2 | 按流哈希 |
| 3 | DATA 逐流喷洒 |
| 4 | AllToAll / FatTree 专项拆分 |

其中 4 是当前代码中用于 AllToAll / FatTree 场景的专项实验模式，不是通用 ECMP 策略。普通实验应优先考虑 0 到 3，并通过日志确认路径分布是否符合预期。

路径选择和队列分类需要一起看。ECMP 决定走哪条物理路径，qid 分类决定进入哪个物理发送子队列。某个实验的慢尾部可能不是 ECMP 没有分散流量，而是多个流在最后物理口上落入同一 qid，导致 round-robin 退化。

### 3.8 配置、配置面板与日志体系

配置和日志不属于数据包主路径，但应该放在第三章末尾说明。原因是配置是对前面各模块的统一控制面，日志是对前面各模块的统一观测面；如果把配置面板放在实现方案开头，会打断“业务流如何进入网络、RoCE 如何发包、队列如何调度、拓扑如何转发”的叙事顺序。

默认配置文件是 simconfig/config.json。主要配置分组如下。

| 分组 | 作用 |
|---|---|
| 顶层字段 | workload 路径、线程数、GPU 类型、pipeline schedule 等 |
| network | ECMP、MTU、普通链路速率、NVLink 速率、链路时延、最大跳数 |
| topology | 拓扑类型、规模参数、external 文件、服务器内 GPU 子网 |
| pfc | PPP 子队列数量、队列容量、PFC 高低水位 |
| roce | RoCE 使能、QP 深度、ACK、窗口、重传、乱序窗口、timeout |
| mactable | MAC 表 load、dump、computed 以及目录 |
| logging | 日志目录、日志文件名、RoCE/PFC/ns-3 component 日志开关 |

配置解析主要位于 scratch/my_common.h。入口程序 scratch/my_AstraSimNetwork.cc 支持默认读取 simconfig/config.json，也支持通过 network_conf 或 -c 指定其他配置文件。

第三阶段还实现了轻量本地网页配置面板。该面板读取并写回 simconfig/config.json，按基础、拓扑、网络与 ECMP、PFC 与队列、RoCE、MAC 表、日志、专家 JSON 等分组展示字段。普通用户只看到常用字段；不同拓扑下隐藏不生效字段；保存前生成备份；隐藏字段不删除，以保证旧配置和专家配置能继续 round-trip。

日志体系按层次组织。

(1) 主程序日志：network drained、last FLOW_TX_DONE、total send count、total events，用于判断整体收尾时间和网络活动结束时间。

(2) Flow 事务日志：TriggerSendTo_now、REQ_DONE、RX_DONE、TX_DONE，用于判断上层是否下发 flow，以及三阶段事务是否闭环。

(3) RoCE 传输日志：ROCE CFG、ROCE ACTIVE、ACK、RTO、RTX、乱序处理、SQ/RQ/CQ，用于判断 RoCE 运行时是否激活，以及是否进入重传或乱序路径。

(4) Bridge/PFC 日志：NO_PATH、terminal drop、PFC pause/resume、bridge drop summary，用于判断路径、回压和 bridge 转发问题。

(5) ECMP 日志：候选端口、实际出端口、flow tuple，用于解释多路径选择结果。

诊断时应先看上层是否下发 flow，再看 RoCE 是否激活，再看三阶段事务是否闭环，最后根据异常信号进入传输恢复、PFC、MAC 学习、ECMP 或队列分类分析。

### 3.9 当前模型边界

当前模型可以称为面向网络行为的 RC-like RoCE 近似模型，不能称为完整现实 RoCEv2/RNIC 模型。

已经具备的网络行为包括：

(1) QP、PSN 和有序接收。

(2) 每 QP 未确认窗口。

(3) 传输层 ACK。

(4) 超时、重传和恢复状态。

(5) 有界乱序缓存。

(6) 感知 PFC pause 的端口准入。

(7) 绑定物理端口的报文级运行时。

仍保留的主要简化包括：

(1) 不是完整 verbs 级 QP 生命周期。

(2) 没有完整 PD/MR/SRQ 资源模型。

(3) RQ 不是完整 posted receive 和 RNR 语义。

(4) CQ 不是上层唯一完成驱动。

(5) 主路径不是现实常见 RoCEv2 over UDP/IP。

(6) 没有完整 ECN/CNP/DCQCN 拥塞控制闭环。

(7) 多 rail striping 和多端口 QP 绑定仍未进入主逻辑。

这些边界需要在实验解释中明确说明。当前版本适合分析 RoCE-like 可靠传输、PFC、队列、路径选择和训练通信尾部行为；如果要对标真实大规模 RoCEv2 集群的拥塞控制，还需要继续补充外层协议、ECN/CNP/DCQCN 和多 rail 相关模型。

## 4. 仿真实验

第三阶段最重要的目标有三：RoCE 主路径是否能闭环，仿真器整体能否符合验收标准，即与实机相比误差小于 15%，十万卡仿真能否运行。本章主要围绕这三个问题阐述。

### 4.1 实验口径与观察方法

当前实验默认使用项目根目录下的 ns-3 入口运行，常见入口是 scratch/my_AstraSimNetwork.cc。默认配置文件是 simconfig/config.json，日志目录是 simlog。运行时如果通过 network_conf 或 -c 指定其他配置文件，则应以命令行指定的配置为准。

实验分析主要看三类时间口径。

(1) all passes finished：Astra-Sim workload 或 stream 层完成时间，反映上层调度视角。

(2) last FLOW_TX_DONE：最后一个三阶段业务事务闭环时间，更适合判断业务通信完成。

(3) network drained：sendflowclient 视角下最后一次网络活动时间，更接近网络侧最后报文活动结束。

这三个时间不是同一个口径。分析网络行为时，通常优先看 last FLOW_TX_DONE 和 network drained，同时说明使用的是哪一个口径。

实验中还需要关注以下异常信号。

(1) RTO 和 RTX：说明传输层超时和重传介入。

(2) REORDER_OVERFLOW：说明接收侧乱序窗口不足或乱序程度过高。

(3) SQ_FULL 和 RQ_FULL：说明发送队列或接收资源达到上限。

(4) NO_PATH 和 DROP：说明路径、MAC 学习或 bridge 处理存在问题。

(5) RX_DONE / TX_DONE spread：说明不同 flow 完成时间的离散程度，可用于观察尾部流。

### 4.2 800 卡实机对比实验

本实验用于验证仿真器整体精度是否达到验收要求。验收口径是：同一类通信任务下，仿真值与实机值相比，误差应小于 15%。本实验选择 800 卡 Clos 拓扑和一层 AllGather 作为对比对象，原因是该场景规模足够大，可以覆盖多交换机、多路径和 RoCE 主路径，同时又有对应实机数据可以比较。

实验设置如下。

| 项目 | 内容 |
|---|---|
| workload | simworkload/800_clos_ring.txt |
| 拓扑 | Clos |
| GPU 数 | 800 |
| spine 交换机 | 12 个 |
| leaf 交换机 | 25 个 |
| leaf 下挂终端 | 每个 leaf 连接 32 个终端 |
| 终端建模 | 每个终端视为一张卡 |
| TP | 800 |
| 其他通信组 | 本场景中可认为不存在 |
| 通信模式 | 一层 AllGather，按 ring 转一圈 |
| RoCE | 启用 |
| 普通链路速率 | 256Gbps |
| MTU | 4096B |
| 交换机静态时延 | 12us |
| MAC 表 | 从已有目录加载 |
| PPP 子队列数量 | 17 |

该场景中，交换机队列容量和 RoCE 发送窗口相对于当前测试流量可以认为足够大。因此，实验重点不是考察拥塞恢复，而是验证拓扑、链路速率、交换机时延、RoCE 主路径和 ring AllGather 展开后，最终通信时间是否接近实机结果。

对比结果如下。

| 数据量(B) | 实机值(us) | 仿真值(us) | 差值 |
|---:|---:|---:|---:|
| 8192 | 51602.81 | 58169 | 11.29% |
| 16384 | 54115.46 | 58374.3 | 7.30% |
| 32768 | 57515.15 | 58785.8 | 2.16% |
| 65536 | 58284.97 | 59609.6 | 2.22% |
| 131072 | 59989.68 | 61257.4 | 2.07% |

该结果可以从三个角度理解。

(1) 所有数据量下，仿真误差均小于 15%，满足验收要求。最大误差出现在 8192B，为 11.29%；其余数据量误差均低于 8%。

(2) 数据量变大后，误差明显下降。32768B、65536B、131072B 三组结果的误差约为 2%，说明在中等及以上消息大小下，链路速率、交换机静态时延和 ring AllGather 展开方式与实机结果较为接近。

(3) 小数据量下误差较大，主要说明固定时延、启动开销、实机软件栈细节和仿真抽象之间仍存在差异。该差异没有超过验收阈值，但后续如果要进一步提高小包精度，需要继续校准端侧固定开销和实机通信库行为。

本实验说明，在 800 卡 Clos 实机对比场景中，当前仿真器可以达到误差小于 15% 的验收标准。由于该场景启用了 RoCE 主路径，且完成了端到端 ring AllGather，因此也从侧面验证了 RoCE 主路径可以承接真实规模的集合通信任务。

### 4.3 六万卡与十万卡规模测试

本实验用于验证仿真器在大规模 AI 集群场景下的可运行性。重点不是对比实机精度，而是确认在六万卡和十万卡级别，拓扑构建、Astra-Sim 通信展开、RoCE 主路径、并行运行和内存占用是否仍然可控。

六万卡实验设置如下。

| 项目 | 内容 |
|---|---|
| GPU 数 | 65536 |
| 拓扑 | k=32 的 FatTree |
| 服务器内子网 | fullmesh，一机 16 卡 |
| TP | 128 |
| DP | 32 |
| EP | 32 |
| PP | 16 |
| 通信量大小 | 2048 |
| workload | 一层 ALLGATHER |
| 总发包数 | 8323072 |
| 发包数公式 | (65536 / 128) * 128 * (128 - 1) |
| 并行方式 | 4 进程 |
| 每进程线程数 | 16 |
| 每进程内存占用 | 约 35G |
| 运行时间 | 跑一层约 20min |

该场景中，TP 为 128，因此每个 TP 通信组包含 128 张卡。一层 ALLGATHER 中，每个组内每张卡需要面向组内其他 127 张卡发起通信。全局共有 65536 / 128 个 TP 组，因此总发包数为 512 * 128 * 127，即 8323072。实验采用 4 个 MPI 进程，每个进程 16 线程并行，单进程内存约 35G，跑完一层约 20 分钟。

十万卡实验设置如下。

| 项目 | 内容 |
|---|---|
| GPU 数 | 108000 |
| 拓扑 | k=60 的 FatTree |
| 服务器内子网 | fullmesh，一机 2 卡 |
| TP | 2 |
| DP | 54000 |
| EP | 54000 |
| PP | 1 |
| workload | 一层通信，保留 TP 相关通信 |
| 总发包数 | 108000 |
| 发包数公式 | (108000 / 2) * 2 * (2 - 1) |
| 并行方式 | 5 进程 |
| 每进程线程数 | 16 |
| 每进程内存占用 | 约 45G |
| 运行时间 | 跑一层约 30min |

十万卡场景是为了测试可行性而设计的特化场景。该场景中 TP 为 2，DP 和 EP 的规模很大，但为了节省静态内存，除 TP 之外的通信组相关部分被注释掉。因此，这个实验不用于说明完整训练 workload 的性能，只用于验证十万卡规模下拓扑、基础通信路径、并行执行和内存占用是否仍能运行。

两组规模实验的结论如下。

(1) 65536 卡场景可以在 4 进程、每进程 16 线程下完成一层 ALLGATHER，单进程内存约 35G，说明六万卡级别的完整通信展开和网络仿真已经具备可运行性。

(2) 108000 卡场景可以在 5 进程、每进程 16 线程下完成特化的一层通信，单进程内存约 45G，说明十万卡规模下仿真器并非只能完成拓扑构建，而是能够进入实际通信运行。

(3) 十万卡实验采用了节省静态内存的特化 workload，因此它证明的是规模可行性，不等同于证明完整十万卡训练 workload 已经可以无条件运行。后续如果要运行完整 DP、EP、PP 通信组，需要继续优化静态内存占用和 workload 展开方式。

### 4.4 External topology 功能验证实验

External topology 实验验证的是另一条能力：拓扑不由 C++ 内置生成，而是由外部文本文件描述时，项目是否仍能正确创建 GPU、交换机、外网链路、内网链路，并让 Astra-Sim workload 在该拓扑上完成通信。

实验设置如下。

| 项目 | 内容 |
|---|---|
| 日志文件 | simlog/external-fattree-k4-gpu4-fullmesh.log |
| 拓扑文件 | simtopo/external-fattree-k4-gpu4-fullmesh.topo |
| workload | simworkload/microAllReduce64_external_fattree.txt |
| GPU 数 | 64 |
| workload 类型 | 64 GPU external FatTree + 4-GPU fullmesh 子网下的 micro AllReduce |

验证重点如下。

(1) topo 文件能够正确解析 GPU 数、交换机数、外网边和内网边。

(2) 每个 GPU 能创建 innerBridge 和 externalBridge 端点。

(3) 外网 GPU 端口加入 external bridge，交换机端口加入 switch bridge。

(4) 内网 GPU-GPU 链路加入 inner bridge。

(5) workload 下发后，flow 事务能够完成。

关键结果如下。

| 指标 | 结果 |
|---|---:|
| FLOW_REQ_DONE | 1208 |
| FLOW_RX_DONE | 1181 |
| FLOW_TX_DONE | 1181 |
| RTO | 0 |
| RTX | 0 |
| REORDER_OVERFLOW | 0 |
| SQ_FULL | 0 |
| RQ_FULL | 0 |
| NO_PATH | 0 |
| DROP | 0 |
| RX_DONE spread | 约 6612.917 us |
| TX_DONE spread | 约 6613.258 us |

结果说明，external topology 构建出的 64 GPU 拓扑能够承接 Astra-Sim workload。日志中没有 NO_PATH 和 DROP，说明该配置下 MAC 学习和路径解析没有明显失败。FLOW_RX_DONE 与 FLOW_TX_DONE 数量一致，说明已经收齐 DATA 的 flow 都完成了发送侧业务闭环。

REQ_DONE 数量高于 RX_DONE 和 TX_DONE，不能简单理解为错误。它需要结合 workload 的分阶段控制流和三阶段事务语义分析。这个实验的主要目的也不是证明 RoCE 传输机制在所有情况下正确，而是证明 external topology v1 能够构建拓扑并支撑 flow 路径可用。

External topology v1 仍有边界。它不表达每链路速率、延迟、plane、rail、pod 层级，也不自动计算 max_jump。因此，在更复杂外部拓扑下，仍需人工检查 network.max_jump、warmup 时间和 ACK timeout。

### 4.5 综合结论与验收口径

第三阶段的实验结论可以按三个目标归纳。

(1) RoCE 主路径是否能闭环。800 卡实机对比场景启用了 RoCE，并完成一层 ring AllGather；External topology 场景也能完成 flow 事务闭环。结合前面实现部分说明，当前 RoCE 主路径已经能够从 Astra-Sim 业务流进入 RoceTransportEngine 和 RdmaPortEngine，并最终回到三阶段业务完成。

(2) 仿真器整体是否满足实机误差小于 15% 的验收标准。800 卡 Clos 实机对比中，五组数据量的误差分别为 11.29%、7.30%、2.16%、2.22%、2.07%，全部小于 15%。其中中等及以上消息大小的误差约为 2%，说明仿真器在该验收场景下已经达到精度要求。

(3) 十万卡仿真能否运行。65536 卡实验可以完成一层 ALLGATHER，108000 卡实验可以完成特化的一层通信。后者虽然不是完整训练 workload，但已经证明十万卡规模下仿真器能够完成拓扑构建并进入通信运行阶段。

需要说明的是，十万卡场景当前仍有明确边界。为了节省静态内存，108000 卡实验注释了除 TP 之外的通信组相关部分。因此，它是规模可行性实验，不是完整十万卡训练负载的最终性能实验。

后续如果继续推进，应优先解决两类问题。

(1) 完整大规模 workload 的静态内存占用。尤其是 DP、EP、PP 等大通信组同时存在时，需要进一步优化 workload 展开和通信组存储方式。

(2) 十万卡完整通信实验的运行时间和多进程内存均衡。当前 108000 卡特化实验每进程约 45G，后续完整场景需要继续控制单进程内存峰值，并结合更多进程划分做并行效率评估。
