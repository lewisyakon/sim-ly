## 1. 手册定位

本文面向需要运行、配置和分析本项目仿真结果的使用者，重点说明第三阶段已经成型的 RoCE 网络仿真路径。本文不作为源码设计文档的替代；涉及 RoCE 内部实现、端点 bridge、可靠性机制和现实匹配性的细节，应继续参考 `src/min-hop-mac-learning/doc/` 下的专题文档。

当前项目的目标是面向 AI 训练集群，在万卡、十万卡规模上进行高精度网络仿真。项目继承自 SIMAI / Astra-Sim，上层调度和 workload 解析保留较多原有结构，主要新增和重构集中在网络侧：

- `src/min-hop-mac-learning/`：第三阶段网络侧主要实现，包括 RoCE transport、端口 runtime、PFC、bridge、MAC 学习、队列和相关文档。
- `scratch/`：仿真入口和拓扑构建代码，当前主入口是 `scratch/my_AstraSimNetwork.cc`。
- `simconfig/`：全局配置文件目录，默认配置是 `simconfig/config.json`。
- `simworkload/`：Astra-Sim workload 输入文件目录。
- `simtopo/`：外部拓扑文件目录。
- `simlog/`：仿真日志输出目录。

第三阶段最重要的变化是：当前 `roce.enable=true` 时，网络主路径已经不是早期简单 3P 旁路，而是一个服务网络行为仿真的 `RC-like` RoCE 近似模型。它已经具备 QP/SQ/RQ/CQ 最小模型、transport ACK、per-QP outstanding window、timeout/retransmission、reorder buffer、pause-aware admission、PFC 和物理端口队列调度等机制。但它仍不是完整 RNIC、verbs、RoCEv2、ECN/CNP/DCQCN 模型。

## 3. 环境准备

本项目基于 ns-3，并启用 MTP / MPI 相关能力。当前环境如果已经能在项目根目录执行 `./ns3 build` 和 `./ns3 run`，则可以直接跳到第 4 节。

首次配置环境时，常用依赖包括：

```bash
sudo apt install g++ python3 cmake ninja-build git -y
sudo apt install ccache python3-pip -y
sudo apt install openmpi-bin openmpi-common openmpi-doc libopenmpi-dev -y
sudo apt install mercurial unzip gdb valgrind clang-format -y
sudo apt install doxygen graphviz imagemagick -y
sudo apt install gsl-bin libgsl-dev libgslcblas0 -y
sudo apt install sqlite sqlite3 libsqlite3-dev -y
sudo apt install libxml2 libxml2-dev libboost-all-dev nlohmann-json3-dev -y
python3 -m pip install --user cppyy
```

构建项目：

```bash
./ns3 configure --enable-mtp --enable-mpi --disable-werror
./ns3 build
```

说明：

- `--enable-mtp` 用于启用多线程并行仿真相关支持。
- `--enable-mpi` 用于启用 MPI 运行支持。
- `--disable-werror` 避免把第三方或历史代码中的 warning 直接升级为构建失败。

如果只是在已经配置好的机器上运行已有实验，通常不需要重复安装依赖，只需要重新执行 `./ns3 build`。

## 4. 快速运行

建议按下面顺序完成一次实验：

1. 确认 `simconfig/config.json` 中的 `workloadpath`、`topology`、`roce`、`logging` 等字段。
2. 如有需要，启动配置面板修改配置并保存。
3. 构建或增量构建项目。
4. 运行仿真。
5. 按 `logging.dir + logging.simulation_log` 查看日志。
6. 先确认 RoCE 激活和 flow 闭环，再分析尾延迟、队列和异常日志。

在项目根目录执行：

```bash
time ./ns3 run my_AstraSimNetwork.cc --command-template "mpirun -np 1 %s"
```

这条命令的含义是：

- `./ns3 run my_AstraSimNetwork.cc`：使用 ns-3 入口运行 `scratch/my_AstraSimNetwork.cc`。
- `--command-template "mpirun -np 1 %s"`：通过 MPI 启动一个进程运行仿真。
- `time`：记录真实墙钟运行时间，便于估计实验成本。

默认情况下，入口程序会读取：

```text
simconfig/config.json
```

如果需要临时使用另一份配置文件，可以用 `network_conf` 指定：

```bash
time ./ns3 run "my_AstraSimNetwork.cc --network_conf=simconfig/your_config.json" --command-template "mpirun -np 1 %s"
```

也可以使用短参数：

```bash
time ./ns3 run "my_AstraSimNetwork.cc -c simconfig/your_config.json" --command-template "mpirun -np 1 %s"
```

不建议把 `network_conf` 写进 `command-template` 里。`command-template` 只负责说明如何启动可执行文件，仿真程序参数应放在 `./ns3 run "程序名 参数"` 这一层，避免 ns-3 wrapper 与 MPI 参数解析混在一起。

如果需要跨多台服务器运行 Docker + Open MPI + ns-3/AstraSim，请先按第 18 节完成 NFS、容器、SSH、`mpi-docker-agent`、物理网卡路由和 Open MPI 基础测试。单机命令能运行不代表多机 MPI 数据面已经可用，多机环境应先通过 `/bin/hostname` 和 CPU 绑定测试，再运行仿真程序。

运行完成后，优先检查配置中指定的日志文件。例如当前 `simconfig/config.json` 中：

```json
"logging": {
  "dir": "simlog",
  "simulation_log": "128_random_test.log",
  "nccl_log": "128_random_test.log"
}
```

对应主日志是：

```text
simlog/128_random_test.log
```

## 5. 配置方式

### 5.1 默认配置文件

默认配置文件是：

```text
simconfig/config.json
```

主要配置分组包括：

- 顶层字段：`workloadpath`、`thread`、`gpu_type`、`pp_schedule` 等。
- `network`：ECMP、MTU、链路速率、链路时延、最大跳数。
- `workload`：warmup / flood 时间等 workload 相关参数。
- `logging`：日志目录、日志文件名、RoCE/PFC/ns-3 component 日志开关。
- `mactable`：MAC 表加载、导出和目录。
- `pfc`：PPP 队列数量、队列容量、PFC 高低水位。
- `topology`：拓扑类型、拓扑规模、外部拓扑文件、服务器内 GPU 子网模型。
- `roce`：RoCE 是否启用、QP 深度、ACK、重传、窗口、乱序窗口、超时等参数。

配置入口和解析位置主要是：

- `scratch/my_AstraSimNetwork.cc`：处理入口参数、日志路径、运行收尾时间。
- `scratch/my_common.h`：读取 `config.json`，解析网络、拓扑、PFC、RoCE、MAC 表等配置。
- `src/min-hop-mac-learning/model/my_sendflowclient.cc`：接收 RoCE 配置，初始化端口 runtime，输出 flow 事务日志。

### 5.2 本地网页配置面板

项目提供了一个轻量本地网页，用来编辑 `simconfig/config.json`：

```bash
python3 tools/config-ui/server.py --host 127.0.0.1 --port 8765
```

启动后在浏览器打开：

```text
http://127.0.0.1:8765/
```

配置面板会：

- 读取 `simconfig/config.json`。
- 按基础、拓扑、网络与 ECMP、PFC 与队列、RoCE、MAC 表、日志、专家 JSON 分组展示。
- 根据拓扑隐藏当前不生效的字段。
- 保存时写回 `simconfig/config.json`。
- 保存前生成备份 `simconfig/config.json.bak`。

注意：

- 配置面板只是 JSON 编辑器，不会自动运行仿真。
- 页面隐藏字段不代表代码不支持该字段；隐藏通常表示普通用户不需要改。
- External 拓扑下，页面当前不会解析 `.topo` 文件并自动推导 MAC 表目录。
- 如果需要修改历史兼容字段或实验字段，应使用“专家 JSON”页。

## 6. 工作负载配置

工作负载文件由顶层字段 `workloadpath` 指定。例如：

```json
"workloadpath": "simworkload/128_test.txt"
```

项目中已有若干 workload 示例：

- `simworkload/microAllReduce.txt`
- `simworkload/microAlltoAll.txt`
- `simworkload/microAllReduce4_external.txt`
- `simworkload/microAllReduce64_external_fattree.txt`
- `simworkload/128_test.txt`
- `simworkload/1024_7B.txt`
- `simworkload/8192_7B.txt`
- `simworkload/16000_13B.txt`

运行前应确认 workload 声明的 GPU 数和拓扑派生出的 GPU 数一致。当前入口程序会检查 workload header 中的 `all_gpus` 与拓扑 GPU 数，如果不一致，会输出类似：

```text
[ConfigMismatch] workload all_gpus=... but topology GPUs=...
```

出现这个错误时，应检查：

- `workloadpath` 是否指向预期文件。
- `topology.model`、`topology.k`、`topology.subnet_model`、`topology.subnet_k` 是否共同派生出正确 GPU 数。
- External 拓扑文件首行的 GPU 数 `N` 是否与 workload 一致。

## 7. 拓扑配置

拓扑配置位于：

```text
topology
```

当前普通配置主要面向：

- `fattree`
- `clos`
- `fullmesh`
- `torus`
- `external`

历史上还存在 `test`、`hpn` 等路径，普通用户不建议在正式实验中直接使用。

### 7.1 FatTree

FatTree 下 `topology.k` 是 k-ary FatTree 参数。代码中常用派生关系是：

```text
numHosts = k^3 / 4
numCores = (k/2)^2
numAggregations = k^2 / 2
numEdges = k^2 / 2
switch_num = numCores + numAggregations + numEdges = 5k^2/4
```

如果同时启用 GPU 子网，最终 GPU 数还会受到 `subnet_model` 和 `subnet_k` 影响。

### 7.2 Clos

Clos 下：

```text
numSpine = k / 2
numHosts = k * hostperleaf
```

其中 `hostperleaf` 表示每个 leaf 下挂多少 host/server 位置。

### 7.3 GPU 子网

服务器内 GPU 子网由 `subnet_model` 和 `subnet_k` 控制：

| `subnet_model` | 含义 | GPU 数派生 |
|---:|---|---|
| `0` | 无服务器内网 | `gpus_per_server=1` |
| `1` | NVSwitch | `gpus_per_server=subnet_k` |
| `2` | GPU FullMesh | `gpus_per_server=subnet_k` |
| `3` | GPU Torus | `gpus_per_server=subnet_k * subnet_k` |

External 拓扑不使用 `subnet_model` 自动生成内网链路，内外链路直接由 `.topo` 文件描述。

### 7.4 External 拓扑

当：

```json
"topology": {
  "model": "external",
  "file": "simtopo/example.topo"
}
```

仿真器会读取外部拓扑文件。当前 v1 文件格式是行式整数边列表：

```text
N M
K
Q0 P0
...
V
Q0 P0
...
```

含义：

- `N`：GPU 数量。
- `M`：交换机数量。
- `K`：外网链路数量。
- 接下来 `K` 行：外网 `normal_link` 边。
- `V`：内网链路数量。
- 接下来 `V` 行：内网 `nvlink` 边。

编号规则：

```text
GPU:    0, 1, ..., N-1
Switch: N, N+1, ..., N+M-1
```

外网链路合法组合：

```text
GPU - Switch      合法
Switch - GPU      合法
Switch - Switch   合法
GPU - GPU         非法
```

内网链路合法组合：

```text
GPU - GPU         合法
GPU - Switch      非法
Switch - GPU      非法
Switch - Switch   非法
```

External 拓扑下需要特别注意：

- `network.max_jump` 不会由 `.topo` 文件自动推导。
- `workload.floadtime_s` 只控制 warmup 时间窗口，不等于泛洪最大跳数。
- `ack_timeout_mode="auto"` 会间接使用 `max_jump` 估算 timeout 基线。
- 如果拓扑较深或链路参数复杂，建议检查 `max_jump` 和 ACK timeout 是否足够保守。

## 8. 网络与 ECMP 配置

网络配置位于：

```text
network
```

常用字段：

```json
"network": {
  "ecmpmodel": 4,
  "max_jump": 5,
  "mtu": 4096,
  "normallink_rate": "224Gbps",
  "nvlink_rate": "2400Gbps",
  "normallink_delay": "5ns",
  "nvlink_delay": "15ns"
}
```

上面是当前工作区的示例片段，不是通用推荐值。正式实验应以本次实验的拓扑、workload 和验证目标为准。

字段说明：

- `ecmpmodel`：多路径选择策略。普通配置面板会用文字展示常用值；如果 JSON 里使用实验值，应以当前代码行为为准。
- `max_jump`：MAC 学习泛洪最大跳数，也影响 RoCE auto ACK timeout 的拓扑预算。
- `mtu`：二层 MTU，单位字节。
- `normallink_rate`：外部网络链路速率。
- `nvlink_rate`：服务器内链路速率。
- `normallink_delay`：外部网络链路传播时延。
- `nvlink_delay`：服务器内链路传播时延。

常用 ECMP 语义：

| 值 | 常见含义 | 使用建议 |
|---:|---|---|
| `0` | 随机转发 | 调试随机路径或对照实验时使用 |
| `1` | 按包哈希 | 兼容旧实验，可能引入包级路径变化 |
| `2` | 按流哈希 | 普通多路径实验优先考虑 |
| `3` | DATA 逐流喷洒 | DATA 流按负载选择端口，适合观察逐流分散效果 |
| `4` | AllToAll / FatTree 专项拆分 | 当前代码中存在的专项实验模式，普通 UI 不作为正式下拉选项 |

`ecmpmodel=4` 是当前代码中用于 AllToAll/FatTree 场景的专项路径选择模式，会根据物理源/目的和 FatTree 层级做固定拆分；它不是通用 ECMP 策略。普通用户应优先使用配置面板公开的 0..3 选项，只有在复现实验或明确需要该专项模式时才使用 4。

## 9. MAC 表配置

MAC 表配置位于：

```text
mactable
```

常用字段：

```json
"mactable": {
  "load_enable": false,
  "dump_enable": false,
  "computed_enable": true,
  "dir": "mactable"
}
```

含义：

- `load_enable=true`：从已有目录加载 MAC 表，减少 warmup/flood 成本。
- `dump_enable=true`：在泛洪学习后导出 MAC 表。
- `computed_enable=true`：使用计算式 MAC 表能力。当前只支持 `FatTree + subnet_model=2`，且不能同时打开 `load_enable` 或 `dump_enable`。
- `dir`：MAC 表目录。

典型流程：

1. 第一次对新拓扑运行时，可关闭 load、打开 dump，生成 MAC 表。
2. 后续同一拓扑重复实验时，可打开 load、关闭 dump，减少泛洪等待。
3. 内置拓扑建议使用配置面板自动生成 MAC 表目录，避免手写 scenario tag 出错。

如果运行时提示 MAC 表加载失败，不应继续把结果当成有效实验结果。入口程序会在 load 失败时中止，以避免在不完整转发表上继续跑 workload。

## 10. PFC 与队列配置

PFC 和 PPP 队列配置位于：

```text
pfc
```

示例：

```json
"pfc": {
  "drop_tail_queue_size": "5000000",
  "drop_tail_queue_num": "17",
  "high_watermark": 0.8,
  "low_watermark": 0.2,
  "not_head_retry_ns": 1
}
```

上面同样是当前工作区示例。`drop_tail_queue_num=17` 和历史实验中的 `13` 都应理解为特定 workload 下的实验设置，不应直接写成所有实验的推荐值。

字段说明：

- `drop_tail_queue_num`：`PppRoundRobinQueue` 的子队列数量，也会影响 `RdmaPortEngine` 的 qid/pause/admission 组织。
- `drop_tail_queue_size`：每个 PPP 子队列容量。
- `high_watermark`：PFC pause 水位。
- `low_watermark`：PFC resume 水位。
- `not_head_retry_ns`：历史兼容字段，当前 bridge ingress 已改为 token-based drain/retry，不再使用旧的 not-head retry 队首模型。

应满足：

```text
0 <= low_watermark < high_watermark <= 1
```

第三阶段需要特别注意 `drop_tail_queue_num`。近期 128 GPU AllToAll 排查发现，PPP 子队列当前按目的 MAC hash 分桶，当队列数和 MAC 地址规律形成别名碰撞时，多个目的流可能落入同一子队列，RR 退化为子队列内 FIFO。某些实验中 `13` 或 `17` 这类队列数可以打破特定碰撞，但这不是长期机制本身。长期更稳健的方向是 flow-aware qid classifier 或 per-flow DRR。

## 11. RoCE 配置

RoCE 配置位于：

```text
roce
```

示例：

```json
"roce": {
  "enable": true,
  "mode": "rc_3phase",
  "data_use_write": true,
  "sq_depth": 1024,
  "rq_depth": 1024,
  "transport_ack_enable": true,
  "transport_window_packets": 500000,
  "reorder_window_packets": 400000,
  "ack_timeout_mode": "auto",
  "ack_timeout_factor": 10000.0,
  "ack_timeout_ns": 10,
  "max_retransmissions": 8,
  "ether_type": "0x9999"
}
```

这段示例来自当前工作区配置，主要用于 128 GPU AllToAll 相关实验。特别是 `transport_window_packets=500000`、`reorder_window_packets=400000`、`ack_timeout_factor=10000.0` 都是偏保守或偏实验的取值，不代表所有规模和拓扑的默认推荐。

字段说明：

- `enable`：是否启用 RoCE 路径。`true` 时发送/接收路径会附加并解析 `RoceSimHeader`，启用 QP/FSM/ACK/重传等语义。
- `mode`：历史/高级字段，当前常见值是 `rc_3phase`。普通用户一般不需要修改。
- `data_use_write`：DATA 阶段是否默认使用 RDMA WRITE 语义。
- `sq_depth`：默认 QP Send Queue 深度。
- `rq_depth`：默认 QP Receive Queue 深度。
- `transport_ack_enable`：是否启用 transport ACK、timeout、retransmission。
- `transport_window_packets`：每个 QP 同时允许 outstanding 的 packet 上限。
- `reorder_window_packets`：接收侧允许缓存的 future packet 乱序窗口。
- `ack_timeout_mode`：ACK timeout 来源，常用 `auto` 或 `fixed`；历史 `manual` 等价于 fixed 语义。
- `ack_timeout_factor`：auto 模式下乘在 RTT 基线上的放大系数。
- `ack_timeout_ns`：fixed/manual 模式下直接使用的 timeout。
- `max_retransmissions`：单个 transport packet 最大重传次数。
- `ether_type`：RoCE-like 报文使用的二层 EtherType。

约束：

```text
1 <= reorder_window_packets <= transport_window_packets
```

使用建议：

- 如果目的是观察无重传干扰下的队列或 ECMP 行为，可以临时使用较大的 `ack_timeout_factor`，但不要把单次实验值当成通用推荐。
- 如果希望研究 retransmission 行为，应使用更接近拓扑 RTT 的 timeout，并打开 RoCE 相关日志。
- 如果 `ack_timeout_mode="auto"`，应同时检查 `network.max_jump`、链路速率、MTU 和 `switch_delay_ns_override`，因为自动 timeout 基线由这些量共同推导。
- 如果出现 `[ROCE][RX][REORDER_OVERFLOW]`，应检查乱序窗口是否过小，或是否存在严重乱序/丢包/路径不稳定。
- 如果出现 `[ROCE][RTO]` 和 `[ROCE][RTX][SEND]`，说明 transport recovery 已经介入，结果分析应把重传成本纳入口径。

## 12. 当前 RoCE 工作流

`roce.enable=true` 时，一条业务流的大致路径是：

```text
Astra-Sim
  -> sendflowclient
  -> RoceTransportEngine::PrepareTxWork
  -> resolve egress port
  -> RdmaPortEngine::PostSend
  -> port-side SQ
  -> RoceTxScheduler
  -> packetize + RoceSimHeader
  -> PointToPointNetDevice::SendFrom
  -> network
  -> peer ingress port
  -> sendflowclient::HandleRead
  -> ingress RdmaPortEngine::HandleIncomingPacket
  -> ready upper payload
  -> sendflowclient::ProcessThreePhasePayload_
```

各层职责：

- `sendflowclient`：Astra-Sim facade 和 3P 业务语义入口，负责 REQUEST/DATA/ACT 业务闭环。
- `RoceTransportEngine`：逻辑层，负责 `flow/lane -> qpn`、`REQUEST/DATA/ACT -> opcode/txClass` 和 3P FSM。
- `RdmaPortEngine`：端口侧 RoCE packet runtime，负责 QP/SQ/RQ/CQ、packetize、ACK、retransmission、reorder、pause-aware admission。
- `MinHopBridgeNetDevice`：MAC 学习、ECMP/flood、真实 outPort 选择、bridge ingress aggregate queue。
- `PointToPointNetDevice + PppRoundRobinQueue`：真实物理发送队列和 per-qid RR 调度。

需要区分两类 ACK：

- transport ACK：RoCE transport 层 ACK，用于 outstanding packet retire、timeout/recovery。
- `ACT`：3P 业务控制报文，用于业务事务闭环和 `[FLOW][TX_DONE]`。

`ACT` 不是 transport ACK。

## 14. 关键日志口径

### 14.1 主程序收尾时间

仿真结束后，入口程序会输出：

```text
[main] network drained abs_time(ns)=... since_workload_start(us)=...
[main] last FLOW_TX_DONE abs_time(ns)=... since_workload_start(us)=...
```

含义：

- `network drained`：`sendflowclient` 视角下最后一次真实网络活动时间，更接近网络侧最后一个包活动结束。
- `last FLOW_TX_DONE`：最后一个 `[FLOW][TX_DONE]` 发生时间，更接近业务事务全部闭环。
- `since_workload_start`：以 Astra-Sim workload `fire()` 时间作为零点。

Astra-Sim 还会输出：

```text
all passes finished at time: ...
```

三者口径不同：

- `all passes finished`：workload / stream 层口径。
- `[main] last FLOW_TX_DONE`：3P 事务层口径。
- `[main] network drained`：网络活动口径。

### 14.2 RoCE 激活日志

典型日志：

```text
[ROCE][CFG] enable=true mode=rc_3phase ...
[ROCE][ACTIVE] node=... mode=rc_3phase ...
```

如果配置中 `roce.enable=true`，但日志中没有 `[ROCE][ACTIVE]`，应检查：

- 配置文件是否是实际运行使用的文件。
- `logging.ns3_components.rdma_port_engine` 或相关 component 是否开启。
- 程序是否在拓扑/配置阶段提前退出。

### 14.3 事务流日志

常见事务日志：

```text
TriggerSendTo_now declared now time = ... src=... dst=... tag=... size=...
[FLOW][REQ_DONE] {tag,src,dst}= ... workId=... TIME=...
[FLOW][RX_DONE] {tag,src,dst}= ... dataPackets=... dataBytes=... TIME=...
[FLOW][TX_DONE] {tag,src,dst}= ... actPackets=... TIME=...
```

含义：

- `TriggerSendTo_now`：Astra-Sim / `my_entry` 已经下发一条点到点事务。
- `[FLOW][REQ_DONE]`：REQUEST 控制 work 的最后一个 slice 已经真正发出。
- `[FLOW][RX_DONE]`：接收侧收齐 DATA 分片，会触发 ACT。
- `[FLOW][TX_DONE]`：发送侧收到 ACT，业务事务闭环。

### 14.4 ACK / 重传 / 乱序日志

常见 RoCE transport 日志：

- `[ROCE][ACK][TX]`：接收侧发出 transport ACK。
- `[ROCE][RX][REORDER_BUFFER]`：future packet 进入 reorder buffer。
- `[ROCE][RX][REORDER_RELEASE]`：连续可交付的 buffered packet 被释放。
- `[ROCE][RX][REORDER_OVERFLOW]`：future packet 超出乱序窗口。
- `[ROCE][RTO]`：最老 outstanding packet 超时。
- `[ROCE][RTX][SEND]`：某个重传包真正发出。

如果实验目标是分析排队或 ECMP，通常希望先确认没有大量 RTO/RTX 干扰。如果实验目标是验证可靠性机制，则应主动打开这些日志并统计触发频次。

### 14.5 Bridge / PFC 日志

常见日志：

- `[BRIDGE][RETRY][NO_PATH]`：普通 forwarding bridge 的某个 ingress 包完成 `switch_delay` 后找不到可用出路，会保留并 retry。
- `[BRIDGE][TERMINAL][DROP]`：终端外侧 bridge 学习后丢弃 transit 包，不承担普通 transit 转发。
- `[PFC][THRESH][LOCAL][PAUSE/RESUME]`：本地注入队列达到高/低水位，通过 `FlowIo` 暂停/恢复本地软件发送队列。
- `[PFC][THRESH][NONLOCAL][PAUSE/RESUME]`：来自真实 ingress port 的队列达到高/低水位，向上游物理口回发 pause/resume。

当前 bridge ingress 是每个 ingress port 一个 aggregate queue，每个包独立 token，经过 `switch_delay` 后 drain/retry。不要再用旧的 per-qid ingress queue 口径解释当前 bridge ingress。

## 15. 推荐排查顺序

一次仿真结果异常时，建议按下面顺序排查：

1. 确认实际使用的配置文件。默认是 `simconfig/config.json`，命令行 `--network_conf` / `-c` 会覆盖。
2. 确认 `workloadpath` 存在，且 workload GPU 数与拓扑派生 GPU 数一致。
3. 确认日志文件路径，即 `logging.dir + logging.simulation_log`。
4. 检查日志中是否出现 `TriggerSendTo_now`，确认上层确实下发了流。
5. 检查是否出现 `[ROCE][ACTIVE]`，确认 RoCE 路径被激活。
6. 检查 `[main] total send count` 是否大于 0。
7. 检查 `[FLOW][REQ_DONE] / [FLOW][RX_DONE] / [FLOW][TX_DONE]` 是否形成闭环。
8. 若 flow 闭环慢，先看是否有 `DROP`、`RTO`、`RTX`、`REORDER_OVERFLOW`、`NO_PATH`、`SQ_FULL`、`RQ_FULL`。
9. 若没有明显丢包/重传，但尾部很慢，检查 `drop_tail_queue_num`、`FLOW_RX_DONE/FLOW_TX_DONE` spread 和 PPP 子队列分类碰撞。
10. 若是 external 拓扑，检查 `.topo` 文件、`max_jump`、MAC 表 load/dump 和 ACK timeout。

## 18. 多机 Docker + Open MPI 运行

本节整合桌面参考文档 `参考文档/ns3_openmpi_multinode_docker_tutorial_v2.md` 的多机配置流程，用于在多台服务器上运行同一个 ns-3/AstraSim 可执行文件。单机实验可以跳过本节。

### 18.1 适用场景与运行模型

多机运行适用于以下场景：

- 仿真规模较大，需要把 MPI rank 分布到多台服务器。
- 使用共享 NFS 工作区，让多台机器运行同一份代码和配置。
- 所有 MPI rank 都希望运行在 Docker 容器内，避免宿主机依赖差异。
- Open MPI 控制面和 TCP 数据面需要固定走物理网卡，而不是虚拟组网接口。

推荐运行模型是：

```text
在主控容器内执行 mpirun
  -> Open MPI 通过 ssh 登录远端宿主机
  -> 远端宿主机执行 /usr/local/bin/mpi-docker-agent
  -> mpi-docker-agent 通过 docker exec 进入本机对应容器
  -> 在容器内执行 /usr/bin/orted
  -> 所有 MPI rank 都运行在容器内
  -> OOB 控制面和 BTL TCP 数据面都走 10.201.0.0/16 物理网络
```

参考环境中的四台机器映射如下：

| 逻辑名 | 物理网 IP | 物理网卡示例 | 容器名 |
|---|---:|---|---|
| `lab188` | `10.201.0.188` | `enp0s31f6` | `hybrid-188` |
| `lab206` | `10.201.0.206` | `eno1` | `hybrid-206` |
| `lab254` | `10.201.0.254` | `eno1` | `hybrid-254` |
| `lab133` | `10.201.0.133` | `enp6s0` | `hybrid-133` |

实际部署时可以替换机器名、IP、网卡和容器名，但四类映射必须在 SSH、hosts、路由、agent 配置和 `mpirun --host` 中保持一致。

### 18.2 前置条件

多机运行前应满足：

1. 所有服务器都挂载同一个 NFS 工作区，例如 `/mnt/nfs/cloud`。
2. 项目代码位于同一路径，例如 `/mnt/nfs/cloud/hybrid`。
3. 所有服务器使用同一个 Docker 镜像，容器内包含同版本 Open MPI 和本项目运行依赖。
4. 容器使用 `--network host`，并挂载 NFS 工作区、宿主机 `.ssh` 目录和当前 SSH agent socket。
5. 宿主机之间、容器到宿主机之间都能通过 SSH agent 免密登录。
6. 每台宿主机都安装 `/usr/local/bin/mpi-docker-agent`，并在 `/etc/mpi-docker-agent.conf` 中配置本机容器名。
7. Open MPI 的 OOB 控制面和 BTL TCP 数据面都固定到 `10.201.0.0/16` 物理网络。
8. 防火墙允许物理网卡上来自其他 MPI 节点的 TCP 入站连接。

不要在 SSH 还不能免密、NFS 还不能写、路由仍走虚拟网卡或普通 TCP 互连还不通时直接调 ns-3 程序。那样很容易把环境问题误判为仿真器问题。

### 18.3 NFS 共享工作区

所有机器建议使用统一路径：

```bash
/mnt/nfs/cloud
/mnt/nfs/cloud/hybrid
```

Open MPI 运行时统一指定：

```bash
--wdir /mnt/nfs/cloud/hybrid
```

NFS 服务端示例：

```bash
sudo apt update
sudo apt install -y nfs-kernel-server
sudo mkdir -p /mnt/nfs/cloud
sudo chown -R 1601:1601 /mnt/nfs/cloud
sudo chmod -R u+rwX,g+rwX /mnt/nfs/cloud
```

`/etc/exports` 示例：

```text
/mnt/nfs/cloud 10.201.0.0/16(rw,sync,no_subtree_check)
```

应用配置：

```bash
sudo exportfs -ra
sudo exportfs -v
sudo systemctl enable --now nfs-server
```

NFS 客户端示例：

```bash
sudo apt update
sudo apt install -y nfs-common
sudo mkdir -p /mnt/nfs/cloud
sudo mount -t nfs <NFS_SERVER_IP>:/mnt/nfs/cloud /mnt/nfs/cloud
```

验证：

```bash
df -h /mnt/nfs/cloud
mount | grep /mnt/nfs/cloud
ls -ld /mnt/nfs/cloud /mnt/nfs/cloud/hybrid
touch /mnt/nfs/cloud/hybrid/.nfs_write_test_$(hostname)
ls -l /mnt/nfs/cloud/hybrid/.nfs_write_test_*
```

如果出现写权限问题，优先检查宿主机用户、容器用户和 NFS 目录的 UID/GID 是否一致。参考 Dockerfile 中 `lympi` 用户 UID/GID 为 `1601` 的设置，不建议直接依赖长期 `no_root_squash`。

### 18.4 Docker 容器要求

四台机器应使用同一个镜像。镜像内至少需要：

- `openssh-client`
- `openmpi-bin`
- `openmpi-common`
- `libopenmpi-dev`
- ns-3/Astra-Sim 构建和运行依赖
- 与 NFS 目录权限匹配的普通用户，例如 `lympi`

构建镜像示例：

```bash
cd /mnt/nfs/cloud/hybrid
sudo docker build -t hybrid-x-lab:v0 -f Dockerfile .
```

验证镜像 Open MPI 版本：

```bash
docker run --rm hybrid-x-lab:v0 mpirun --version | head -1
```

容器必须使用 `--network host`。以 `lab188` 为例：

```bash
docker run -d \
  --name hybrid-188 \
  --network host \
  --memory=160g --memory-swap=160g \
  -v /mnt/nfs/cloud:/mnt/nfs/cloud \
  -v /home/lewis/.ssh:/home/lympi/.ssh \
  -v "$SSH_AUTH_SOCK:/ssh-agent" \
  -e SSH_AUTH_SOCK=/ssh-agent \
  hybrid-x-lab:v0
```

其他机器替换容器名、内存限制和宿主机 `.ssh` 路径。容器启动后检查：

```bash
docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Image}}'
docker exec hybrid-188 bash -lc 'whoami; id; pwd; mpirun --version | head -1; which orted'
```

进入主控容器：

```bash
docker exec -it --user lympi hybrid-188 /bin/bash
cd /mnt/nfs/cloud/hybrid
ssh-add -l
```

如果容器内 `ssh-add -l` 失败，通常说明 `$SSH_AUTH_SOCK` 没有挂对，需要用当前宿主机 SSH agent socket 重建容器。

### 18.5 SSH 与 mpi-docker-agent

先在宿主机之间验证免密 SSH：

```bash
for h in lab188 lab206 lab254 lab133; do
  echo "===== $h ====="
  ssh -o BatchMode=yes "$h" 'hostname; whoami'
done
```

再在主控容器中验证容器到宿主机的免密 SSH：

```bash
for h in lab188 lab206 lab254 lab133; do
  echo "===== $h ====="
  ssh -o BatchMode=yes "$h" 'hostname; whoami'
done
```

`mpi-docker-agent` 的作用是让远端宿主机收到 Open MPI 的 SSH 启动命令后，转入本机容器执行 `orted`。每台宿主机都需要配置本机容器名：

```bash
echo 'MPI_DOCKER_CONTAINER=hybrid-188' | sudo tee /etc/mpi-docker-agent.conf
```

其他机器分别改为 `hybrid-206`、`hybrid-254`、`hybrid-133`。可选追加：

```bash
sudo tee -a /etc/mpi-docker-agent.conf >/dev/null <<'EOF'
MPI_DOCKER_USER=lympi
MPI_DOCKER_WORKDIR=/mnt/nfs/cloud/hybrid
EOF
```

`/usr/local/bin/mpi-docker-agent` 的核心逻辑是读取 `/etc/mpi-docker-agent.conf`，检查对应容器是否运行，然后执行：

```bash
docker exec \
  --user "$MPI_DOCKER_USER" \
  --workdir "$MPI_DOCKER_WORKDIR" \
  "$MPI_DOCKER_CONTAINER" \
  /usr/bin/orted ...
```

远端 SSH 用户必须能无交互执行 `docker exec`。如果需要加入 docker 组，应在宿主机执行：

```bash
sudo usermod -aG docker <SSH_USER>
```

然后重新登录生效。不要依赖 `sudo docker exec`，因为 MPI 远端启动时不能输入 sudo 密码。

从主控容器验证 agent：

```bash
for h in lab188 lab206 lab254 lab133; do
  echo "===== $h ====="
  ssh "$h" '
    hostname
    cat /etc/mpi-docker-agent.conf
    /usr/local/bin/mpi-docker-agent /usr/bin/mpirun --version | head -1
    /usr/local/bin/mpi-docker-agent /bin/hostname
  '
done
```

四台机器应输出同一版本 Open MPI，并且 `/bin/hostname` 能在对应容器内执行。

### 18.6 物理网络、路由与防火墙

推荐统一使用 `10.201.0.0/16` 物理网卡作为 MPI 控制面和数据面。四台宿主机和容器中的 hosts 解析应指向物理网 IP，例如：

```text
10.201.0.188 lab188 seu-Precision-7920-Tower
10.201.0.206 lab206 Super-Server
10.201.0.254 lab254 user-Super-Server
10.201.0.133 lab133 user-System-Product-Name
```

检查路由：

```bash
for ip in 10.201.0.188 10.201.0.206 10.201.0.254 10.201.0.133; do
```


以 `lab133` 为例：


### 18.9 多机排查顺序

多机环境异常时建议按下面顺序排查：

1. NFS：所有机器能否看到同一份 `/mnt/nfs/cloud/hybrid`，并能写入测试文件。
2. 宿主机 SSH：宿主机之间是否能 `ssh -o BatchMode=yes` 免密互连。
3. 容器 SSH：主控容器中是否能免密 SSH 到所有宿主机。
4. 容器状态：每台宿主机的目标容器是否运行，镜像和 Open MPI 版本是否一致。
5. agent：`/usr/local/bin/mpi-docker-agent /bin/hostname` 是否能在远端容器内执行。
6. hosts：`lab188/lab206/lab254/lab133` 是否解析到 `10.201` 物理网 IP。
7. 路由：`ip route get` 是否走物理网卡，而不是 `ztkse63itn` 等虚拟接口。
8. 防火墙：物理网卡是否允许来自其他 MPI 节点的动态 TCP 入站。
9. TCP：`nc` 是否能在宿主机和容器侧连通。
10. Open MPI：`/bin/hostname`、`--display-map`、`--report-bindings` 是否通过。
11. ns-3：再运行实际仿真程序，并按第 14、15 节检查仿真日志。

常见错误：

- `Invalid command-line argument: --host`：多 app context 的 `:` 分隔缺失，导致后续 `--host` 被传给 ns-3 程序。
- `requested more processes than the ppr can support`：`-np` 与 `--map-by ppr:*:node` 不匹配；同一程序不同节点 rank 数时优先用 `--host lab188:2,... -np 5 --map-by slot:PE=16`。
- Open MPI daemon 启动后超时：优先检查 hosts、路由、防火墙、`nc` 和 `--mca *_if_include`，不要只看 SSH。
- `Permission denied (publickey)`：检查 SSH agent、`ssh-add -l`、`ssh -vvv`、远端 `authorized_keys` 和 `.ssh` 权限。
- rank 被 `Killed` 或 signal 9：检查 Docker 内存限制、宿主机 OOM、`dmesg` 和 `journalctl`。
- X11 相关噪音：使用 `env -u DISPLAY -u XAUTHORITY`。

## 19. 常见问题

### Q1：运行后没有看到 RoCE 日志，是否说明 RoCE 没启用？

不一定。先检查 `roce.enable` 是否为 `true`，再检查 `logging.log_levels.roce` 和 `logging.ns3_components` 中相关 component 是否开启。只有配置和 component 日志都满足时，许多 `NS_LOG_INFO` 才会输出。

### Q2：`all passes finished` 和 `network drained` 哪个代表最终性能？

它们代表不同口径。`all passes finished` 是 Astra-Sim workload / stream 层完成时间；`last FLOW_TX_DONE` 是 3P 事务闭环时间；`network drained` 更接近网络侧最后活动时间。分析网络行为时，通常优先看 `last FLOW_TX_DONE` 和 `network drained`，并说明使用的是哪个口径。

### Q3：看到 `RTO` 是否一定说明网络配置错了？

不一定。`RTO` 说明 transport timeout/recovery 介入。它可能来自 timeout 设得过小、排队过长、PFC pause、路径异常、乱序窗口不足或真实丢包。需要同时看 `[ROCE][RTX][SEND]`、`REORDER_OVERFLOW`、PFC、NO_PATH 和 flow 完成时间。

### Q4：为什么调整 `drop_tail_queue_num` 会明显影响 AllToAll 尾部？

当前 PPP 子队列默认按目的 MAC hash 分桶。若目的 MAC 地址规律和队列数取模形成碰撞，多条并发目的流会落入同一子队列，RR 退化为该子队列内 FIFO。换一个队列数可能打破碰撞，但这只是 workload/地址/队列数共同作用下的 workaround，不是长期设计原则。

### Q5：`not_head_retry_ns` 现在还需要调吗？

一般不需要。当前 bridge ingress 已经是 aggregate queue + token-based drain/retry，`not_head_retry_ns` 是历史兼容字段，不再代表旧的队首阻塞 retry 模型。

### Q6：External 拓扑文件能不能表达每条链路不同速率？

当前 v1 不能。`.topo` 文件只表达节点和边，外网统一使用 `network.normallink_rate/normallink_delay`，内网统一使用 `network.nvlink_rate/nvlink_delay`。每链路单独速率、延迟、plane/rail/pod 语义属于后续扩展方向。

### Q7：`roce.enable=true` 是否等于完整真实 RoCE？

不是。当前实现是面向网络仿真的 `RC-like` RoCE 近似模型。它已经包含 ACK、重传、reorder、窗口、PFC 和端口准入等关键网络行为，但没有完整 RNIC verbs、RoCEv2 over UDP/IP、ECN/CNP/DCQCN 闭环。

### Q8：大规模实验前应该先做什么？

建议先在小规模 workload 上确认：

- 配置文件能被正确读取。
- MAC 表 load/dump 路径正确。
- workload GPU 数和拓扑 GPU 数一致。
- RoCE 激活日志存在。
- flow 事务能完整闭环。
- 没有明显 `NO_PATH`、`SQ_FULL`、`RQ_FULL`、大量 RTO 或 reorder overflow。

再逐步放大 GPU 数、workload 层数和日志等级。大规模实验中应避免长期打开过细的 per-packet 日志，否则日志本身会显著影响运行成本和存储占用。

### Q9：多机 `mpirun /bin/hostname` 能运行，是否说明 ns-3 多机仿真一定没问题？

不能。`/bin/hostname` 只验证 Open MPI 启动链路；实际 ns-3 MPI 仿真会进入 `MPI_Isend`、`MPI_Irecv`、`MPI_Allgather`、`MPI_AllReduce` 等数据面和同步路径，才会暴露防火墙、路由、接口选择、内存限制和程序分区问题。因此应继续做 `--display-map`、`--report-bindings`、普通 TCP 连通性和小规模 ns-3 smoke 测试。

### Q10：多机 Docker 环境里为什么建议直接运行 build 目录下的可执行文件？

`./ns3 run` 是开发期 wrapper，适合单机开发和构建目录解析。多机 Open MPI 场景中，rank 会分布到不同宿主机和容器，直接运行共享 NFS 中同一个已构建可执行文件更明确，也能减少 wrapper、MPI 参数和仿真程序参数互相干扰的机会。
